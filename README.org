* What this project is

Everything here is free software. The sources are Org mode files, and the build is a single Emacs Lisp program that exports those files into a static web-site.

A static web-site is a directory of finished HTML, CSS, JavaScript and image files. A web server hands those files to a browser without running any program of its own, so there is no database to administer, no server-side language to keep patched, and no page that can fail to render because a daemon is down. The price is that anything dynamic happens in the browser instead.

That trade is deliberate here, and its consequences shape the whole design:

- *Org is the source of truth.* You write prose, headings, lists, tables and code blocks in Org mode, and the exporter turns them into HTML. There is no second copy of the content in a template language.
- *The build is one file.* =jointhefreeworld-site.el= holds the export backend, the shared page layout, the metadata, the feed and the task entry point. The build script is also its own documentation: every function carries a docstring explaining why it exists.
- *Nothing reaches the reader that a page did not ask for.* The REPL and the tech radar are large JavaScript programs, and a page downloads them only when it names them.
- *Pages degrade gracefully.* Both page scripts render their content in the Org source as well, so a reader without JavaScript still gets every fact the dynamic view shows.

This README explains what you need, how the build works, how to write a page, how to work on the stylesheet and the scripts, how the site is deployed, and which traps to avoid. It assumes you can open a terminal, and it explains the conventions as it introduces them.

* What you need

- *GNU Emacs 29.1 or newer.* Older releases lack parts of the publishing API the build relies on.
- *Git.* The build reads the repository for two things: the short commit hash printed in the footer, and the date each Org file was last changed, which becomes the page's modification date. Without a repository, the build continues and prints =unknown= instead.
- *Network access on the first build.* The build installs its Emacs packages into =./.packages=, a directory of its own rather than your =~/.emacs.d/elpa=.
- *GNU Guix and Maak, optionally.* The task runner described below drives development, linting and deployment. You can publish the site with plain Emacs and skip all of it.
- *Node.js, for stylesheet work only.* The CSS linter is a Node program.
- *Two extra Guix packages, for one task only.* Regenerating the site-wide social card by hand needs Inkscape and pngquant; nothing else touches them.
- *A rasteriser and a font, declared in the manifest.* The per-article social cards are drawn during the build by =rsvg-convert= from librsvg, using the DejaVu fonts; both are in =manifest.scm=, so the build's own environment has what a card needs. A build outside it still succeeds: those pages keep the site-wide card and the log says so once.

The Emacs packages the build installs are =use-package=, =esxml= for building HTML out of s-expressions, =htmlize= for colouring source blocks, =webfeeder= for the RSS feed, and the major modes =haskell-mode=, =rust-mode= and =kotlin-mode=, which fontify code blocks written in those languages. All of them come from MELPA and MELPA Stable, except =use-package=, which is built in.

* How the build works

Publishing the site happens in four stages, in this order:

1. *Export.* =org-publish-all= walks the projects in =org-publish-project-alist= and exports every Org file below =./docs= to HTML below =./public=, drawing each blog article's social card while that article is in front of it and writing the blog's index pages out of the articles they list. The export is forced, so every page is written again rather than skipped as unchanged.
2. *Wrap.* Each exported page passes through a template that adds the document head, the shared header and footer, the metadata and the structured data.
3. *Feed.* The blog articles are collected into =./public/rss.xml=.
4. *Copy.* The contents of =./static= are copied beside the generated pages, together with =robots.txt= and =sitemap.xml=.

The export stage is worth understanding first, because it decides where every URL lives.

** The publish projects

A publish project pairs a directory of Org files with a directory of HTML output. Editing the table in =jointhefreeworld-site.el= moves the pages and their canonical URLs together, because the build reads the URL prefix back out of this same table.

| Project                     | Org sources           | Output             | URL prefix       |
|-----------------------------+-----------------------+--------------------+------------------|
| =jointhefreeworld:main=     | =./docs/home/=        | =./public/=        | =/=              |
| =jointhefreeworld:blog=     | =./docs/blog/=        | =./public/blog/=   | =/blog/=         |
| =jointhefreeworld:documentation= | =./docs/documentation/= | =./public/documentation/= | =/documentation/= |
| =jointhefreeworld:platform= | =./docs/platform/=    | =./public/platform/= | =/platform/=     |
| =jointhefreeworld:portfolio= | =./docs/portfolio/=  | =./public/portfolio/= | =/portfolio/=    |
| =jointhefreeworld:policies= | =./docs/policies/=    | =./public/=        | =/=              |

Every project shares the same properties: Org files only, recursive traversal, a forced export, and the site's own publishing function, which is what gives each page its directory-shaped URL.

The policies project is the one exception to the directory rule. The code of conduct and the AI policy are site-wide documents rather than blog posts, so they publish at the top level, as =/code-of-conduct/= and =/ai-policy/=. Their former blog addresses still exist as forwarding pages.

** The URL layout

A URL should be short enough to say out loud and stable enough to cite. The build gives every page a directory of its own, and a small convention turns the file name into that directory:

| Org file                            | Published as          | Reached at          |
|-------------------------------------+-----------------------+---------------------|
| =docs/home/index.org=               | =public/index.html=   | =/=                 |
| =docs/blog/index.org=               | =public/blog/index.html= | =/blog/=         |
| =docs/blog/articles/lisps/index.org= | =.../lisps/index.html= | =/blog/articles/lisps/= |
| =docs/blog/articles/emacs/emacs-registers.org= | =.../emacs-registers/index.html= | =/blog/articles/emacs/emacs-registers/= |
| =docs/home/404.org=                 | =public/404.html=     | the server's not-found page |

Three rules follow from that table, and you must know them before you name a file:

- An =index.org= file answers at its own directory, so =docs/blog/index.org= is =/blog/= and not =/blog/index/=. A page that is the front door of a directory is always called =index.org=.
- Any other file becomes a lowercased directory named after the file, and inside it the page is =index.html=. The file =Emacs-Registers.org= would answer at =/emacs-registers/=. Write your file names the way you want them to appear in the address bar, because the case you choose here does not reach the URL.
- =404.org= is the one file published as a plain HTML file rather than a directory, because web servers look for that exact name.

Links between your Org files are rewritten to match: a link to =foo.org= becomes a link to =/foo/=, with the extension and the capital letters gone. You can therefore cross-reference pages by their file names and let the build produce the addresses.

*** Why the URL is not the file path

The mapping is not a mirror of the source tree, and that is intentional. A reader never sees =docs/=, never types an =.html= extension, and never learns whether a page lives in a file or a directory. Moving a page between projects changes one table entry, and every canonical URL, social card and feed entry follows it.

** What every page gets

Whatever the content, the wrapper adds the same furniture. Knowing what is automatic keeps you from repeating it in the Org file:

- The document head: character set, viewport, author, the meta description, robots directives, the canonical URL, the complete Open Graph and Twitter card, preloads for the fonts used on first paint, favicon, the RSS link, the speculation rules, and the JSON-LD block. The metadata section later in this manual describes each of them.
- The bar at the top: the wordmark, the five places on it, the four behind =more=, and the theme chooser.
- The hero: a monospaced line naming the part of the site the page belongs to, the page title as a first-level heading, and beneath it the date the page was written and an estimated reading time of at least one minute at a reading speed of 130 words per minute. The reading estimate and the date are left off the landing and index pages, where they would mean nothing.
- The content itself, in a sheet of glass, with a rail beside it on a wide screen that the script fills with the page's own headings.
- The site footer: copyright, licence, the short commit hash of the build, and links to the source code, the feed, the tech radar, the two policies and the top of the page.
- The scripts the page asked for, and nothing else.

Two more touches are worth naming because you will see them in a browser. The theme is restored before the first paint by a tiny inline script, so a reader who chose the dark theme never sees a flash of the light one. And supporting browsers may prerender the page behind a link you point at, which makes navigation feel instantaneous.

** The header and the navigation

The bar's links come from one table in the build script, =jfw/nav-links=, which pairs each label with either a site-relative path or an absolute URL. A second table, =jfw/nav-primary-paths=, says which of them stay on the bar: five places a reader goes next are worth naming, and the four they go once — the two policies, the source host, the professional profile — wait behind a =more= disclosure that is a real =details= element, so it opens with no script at all.

The entry the build marks as current is the longest site-relative link the page sits under, so an article marks its own section rather than the whole blog, and the marker is a dot of gold plus =aria-current="page"= rather than a colour alone, so it survives a reader who cannot see the difference.

Adding a link means adding one entry to =jfw/nav-links= and, unless it belongs behind =more=, one path to =jfw/nav-primary-paths=; the tests check that every link ends up in exactly one of the two groups, so a link cannot go missing between them. A page that no entry covers, such as the portfolio, leaves the bar unmarked.

The footer is written by =jfw/site-footer=: what the site is and who made it on the left, the places that are about the site rather than in it on the right, and the commit hash of the build underneath.

* Writing content

** Keywords a page may set

A page's [[https://orgmode.org/manual/Export-Settings.html][export keywords]] are the page's settings, and the build reads the following ones. All of them are optional; only the title is worth setting on every page.

| Keyword          | What it changes                                                                                      |
|------------------+------------------------------------------------------------------------------------------------------|
| =#+TITLE:=       | The page title, used in the browser tab, the heading, the card and the feed.                          |
| =#+DESCRIPTION:= | The meta description and the card summary.                                                            |
| =#+KEYWORDS:=    | Comma-separated keywords for the meta tag, the article tags and the structured data.                  |
| =#+DATE:=        | The publication date, shown as /written on/ and reported to crawlers and the feed.                    |
| =#+AUTHOR:=      | The author, and the name shown in the feed and beside each entry on an index page.                     |
| =#+SCRIPTS:=     | The page scripts to load. Names are separated by commas or spaces.                                     |
| =#+VIDEO:=       | The identifier of a video to embed at the top of the content.                                          |
| =#+CANONICAL:=   | The canonical URL, when it differs from the page's own address.                                        |
| =#+ROBOTS:=      | The robots directives, replacing the indexable default.                                                |
| =#+OG_IMAGE:=    | The social card image, replacing the one the page would otherwise have.                                |
| =#+OG_LABEL:=    | The label a generated card carries, for a page whose category is not the word that describes it. The category is the default. |
| =#+HIGHLIGHT:=   | Puts the article on the blog's front page. The value is read as a yes unless it is =no=, so a post can say why it is highlighted instead of only that it is. |
| =#+REDIRECT:=    | The destination of a forwarding page: adds a refresh, claims the destination as canonical, and asks crawlers not to index the stub. |

Only two page scripts exist today. Ask for =repl= to place the browser Lisp on a page, and for =radar= to draw the tech radar. A name the build does not recognise is reported in the build log rather than silently ignored, which is the intended way to catch a typo.

** Headings, anchors and containers

Every heading becomes an HTML heading element carrying a small =#= anchor link, so any section of a page can be linked to. The anchor's identifier is derived from the heading text: lowercase, spaces turned into hyphens, punctuation dropped.

Two situations call for a property on the heading:

- =:CUSTOM_ID:= sets the identifier explicitly. You need it whenever a heading repeats on a page, because the derived names would collide. The tech radar needs one per layer per ring for exactly this reason.
- =:HTML_CONTAINER:=, with =:HTML_CONTAINER_CLASS:=, wraps the heading and its subtree in an element of your choosing. The radar's rings are sections produced this way, and the radar script finds them by class.

A heading that names a property block looks as follows:

#+begin_example
,* ✅ Adopt
:PROPERTIES:
:HTML_CONTAINER: section
:HTML_CONTAINER_CLASS: jfw-radar-ring
:CUSTOM_ID: adopt
:END:

,** 🧬 Languages
:PROPERTIES:
:CUSTOM_ID: adopt-languages
:END:

- Guile Scheme and Lisps in general
#+end_example

The leading commas are Org's way of writing a heading inside an example. Org removes them when it renders the example, and you must not remove them from this document: without them the example would end at its first line and the rest of it would become headings of this README.

** Adding a blog article

A blog article lives under =docs/blog/articles/= in the directory of its category, and the category is part of its URL. The categories in use are =ci=, =development=, =emacs=, =freebsd=, =gnu-linux=, =go=, =haskell=, =lisps=, =personal= and =rust=.

To add one:

1. Create =docs/blog/articles/<category>/<name>.org=. The file name becomes the URL, so make it descriptive and lowercased.
2. Start the file with =#+title:=, =#+date:= and, when the article deserves one, =#+description:= and =#+keywords:=. The description is the line the listings and a shared link show, so it is worth writing rather than leaving to the opening paragraph.
3. Set =#+author:= to the name that should appear in the feed.
4. Add =#+HIGHLIGHT: yes= if the article belongs on the blog's front page. Its category page lists it either way.
5. Build the site, and confirm the page appears at the URL you expect.

The listings of the blog are generated during the build, so an article registers itself in its category by existing, and nothing has to be added to a second file. The front page is the one exception that stays a choice, and it is a single keyword in the article; =** Blog listings= below explains both.

** Blog listings

The front page's highlights and every category's list of articles are written during the build, out of the articles themselves. An index page says which listing it shows, and the build fills it in:

#+begin_src org
  #+begin_listing highlighted
  #+end_listing
#+end_src

=highlighted= is the front page's selection: the articles that set =#+HIGHLIGHT:=. =category= is every article of the category the page belongs to, which is how a new article reaches its own category page without anybody adding it. Entries come out newest first, by date, and by title when two articles share a date, so the same sources always give the same page. An entry is the article's date, its title and its =#+DESCRIPTION:=, and nothing else.

Three things are worth knowing before editing an index page:

- The date, the title and the summary are read from the article, so a listing cannot show a title that has been rewritten, or forget an article that has been added. Change the article, never the listing.
- A page that only forwards readers elsewhere is not an article and is left out, which is what keeps the two moved policies out of the category they used to live in.
- The blog index and two category pages keep a short =🔗 Elsewhere= list by hand. Those entries are posts on other sites, and no article carries them.

The build reports how many articles it listed, and an index page that asks for a listing the build does not know is reported by name rather than left blank.

** The tech radar

The tech radar on the FREE stack page, =docs/blog/articles/development/tech-radar.org=, is a JavaScript view of an ordinary Org document. Nothing about the source is special except its shape, and the script reads the document itself, so the Org file remains the only place the entries live.

The document leads with the rings, because that is the question a reader arrives with — /how much do you trust this?/ — and names the layers inside each one:

- Each *ring* is a first-level heading with =:HTML_CONTAINER: section= and =:HTML_CONTAINER_CLASS: jfw-radar-ring=. Only the four names =Adopt=, =Trial=, =Assess= and =Deprecate= are known; the leading emoji is ignored.
- Each *layer* is a second-level heading under a ring. A layer appears in every ring that has entries for it, and the first mention is what fixes its place on the picture, so the wedges read in the order =Adopt= introduces them.
- Each *blip* is a list item under a layer. Its text is the technology, an optional link makes it clickable, and a note after a dash explains why it sits there.
- A parenthesised word says what changed since the previous revision: =(new)=, =(moved in)= or =(moved out)=. The radar reads it and draws the entry accordingly.

The picture keeps its own shape whatever the document's order: a ring is still a band drawn from the middle outwards, a layer is still a wedge, and both are read from the headings rather than from a second copy of them. The full list below the drawing follows the document — the four rings, each folded away until it is asked for, with its layers inside it — so a reader whose browser does not run the script loses the picture and none of the content. If a page has no rings, the script does nothing at all.

** The browser Lisp

The home page carries a small Lisp interpreter written in plain JavaScript, =static/js/guile-repl.js=. To place a REPL on a page, set =#+SCRIPTS: repl= and include the markup the script looks for. The REPL section of =docs/home/index.org= is the reference: a section with the class =jfw-repl= containing a form, an input, an output element and the procedure reference.

The interpreter is a real one, with a reader, proper tail calls, closures, vectors and roughly a hundred primitives. Everything it evaluates runs in the browser tab and never reaches the server, which is both a privacy property and the reason a mistake in a session cannot damage anything but that session.

* Look and feel

The whole design lives in one stylesheet, =static/css/jointhefreeworld.css=, and it is organised around custom properties rather than repeated literals. Reading its =:root= block is the fastest way to learn what the site can look like.

Change a token and every rule that uses it changes with it. If you find yourself writing the same colour twice, the token you wanted is probably missing.

** Glass and depth

The design is one sheet of frosted glass laid over warm paper, and three rules keep it coherent:

- *Blur is spent where content actually moves under a surface.* The sticky toolbar, the code blocks and the floating copy button blur their backdrop, because something scrolls behind them and the blur is visible. The article card is translucent but not blurred: its backdrop is the fixed light of the page, so a blur there would cost a repaint on every scroll frame and show nothing.
- *Every pane shares the same three cues.* A lit top edge and a shadowed bottom edge (=--glass-edge=), a thin border that is brighter than the surface (=--glass-hairline=), and a sheen that fades in from the corner nearest the light (=--glass-sheen=). Together they read as thickness; a translucency on its own reads as a faded rectangle.
- *Depth is two shadows, not one.* A tight contact shadow says the pane touches the page, and a wide ambient one says it floats above it. =--box-shadow-lift= is the same pair, pushed further, for a pane the pointer is on.

The page also carries a grain tile, drawn as an inline SVG and attached to the background of =html= rather than laid over the content, so text stays crisp at any zoom.

** The shape of a page

Every page is the same four things, top to bottom, and the Org file only ever writes the third:

1. *A bar.* One thin pill of glass, pinned to the top: the wordmark on the left, the five places a reader goes next, the four they go once behind =more=, and the theme chooser at the far end where a status item lives. Everything else scrolls underneath it and is blurred by it.
2. *A hero.* A monospaced line naming the part of the site the page is in, the title set as a headline and left-aligned rather than centred, the date and the reading time as a stamp, and a rule of gold that fades out to the right. The hero sits on the paper, not inside the sheet, which is what gives a page a front matter instead of a paragraph that happens to be bigger.
3. *A body.* The article in a sheet of glass, and beside it the rail. The rail takes a column only above 1100 pixels and only once the script has filled it, so a page with two headings, or a reader without scripting, gets the whole width for its text.
4. *A footer.* Two columns: what the site is and who made it, then the places that are about the site rather than in it.

The document also keeps two measures on purpose: prose stops at 80 characters and code blocks run to 128, so a wide screen gives its extra room to the code rather than to a line of text that gets harder to read the longer it is.

** Themes

The site follows the reader's system preference by default and lets them override it, in either direction, with the chooser in the header. Three states exist: /system/, /light/ and /dark/, and the choice is remembered in the browser's local storage under a single key shared by the inline script and the chooser.

The two palettes are not each other's inverse, and they are not the same idea twice:

- *Light is warm paper.* Cream newsprint, terracotta links, a pumpkin glow: a printed page with a lamp near it.
- *Dark is graphite.* The neutrals are the greys a Mac uses for its windows, panels and separators — a near-black page, panels a step lighter, hairlines of white at about a tenth of an opacity — and the warmth is spent only where it carries meaning: a link, the place the reader is, the rule under a title, a keyword in a code block. That restraint is the whole trick: orange reads as an accent on grey and as a wash on brown.

Surfaces get lighter as they get closer to the reader, which is the one rule that makes a stack of dark panes read as depth rather than as a flat field. When you edit one of the two palettes, edit its twin in the system-preference block as well; the comment beside each reminds you, and the build's =theme-color= values must agree with both.

** Accessibility commitments

These are not aspirations; the stylesheet and the build enforce them, and a change that breaks one is a regression:

- Colour contrast. Body text and link text clear the WCAG AA thresholds in both themes.
- Focus. Interactive elements take a visible focus ring, and the header's current page is announced rather than only coloured. The first thing Tab reaches is a link past the toolbar.
- Motion. The parenthesis rain, the caret after the tagline, the scroll reveal and the theme cross-fade all stop when the reader asks for reduced motion, and the reveal is written so that a reader who asks for less motion is never shown a hidden section in the first place.
- Transparency. A reader who asks their system for more contrast gets opaque paper instead of glass.
- Structure. The document declares its language, the theme chooser is a group of labelled controls, headings nest properly, and the radar and the REPL expose their content as ordinary markup as well.

** The chrome around the page

Five small pieces of furniture sit around the page. One is written by the build; the other four are drawn by =freeworld.js= and the stylesheet, and are inert until the script runs, so a reader without JavaScript loses none of the content:

- *The rail.* The page's own =h2= and =h3= headings, as a list to jump by, beside the sheet on a screen wide enough to afford the column. It is written by the build rather than by a script, so it is part of what a reader receives; a heading inside a closed disclosure is left out of it; and what the script adds is the mark that follows the reader down it. The build gives it a column only when it has at least three entries, which is why a short page has no empty gutter.
- *The reading progress line.* A hairline of gold across the top of the window that fills as the page is read. The stylesheet draws it from a custom property and the script writes that property, measured in the scroll handler rather than in a frame it would have to wait for.
- *The copy buttons.* Every code block in an article gets a button in its corner that puts the block on the clipboard, using the clipboard API where the page is a secure context and a hidden text area where it is not.
- *The scroll reveal.* The blocks of an article fade and rise as they are reached. The class that hides them is added by the script, so nothing is ever hidden when the script is absent.
- *The skip link.* The first thing Tab reaches is a way past the bar. It is real markup rather than a scripted control, and =#content= carries =tabindex="-1"= so that taking it moves focus into the article.

The rule behind all of this is worth stating plainly: *a page's content never depends on a script*. The rail, the listings, the code blocks and every word of an article are in the HTML the server hands over. What the scripts add is comfort — a mark that follows you, a line that fills, a button that copies — and each of them is written so that its absence is invisible rather than broken. The one deliberate exception is the theme chooser, which is hidden until the inline script marks the document as script-capable: a control that could not remember a choice between two pages would be worse than no control at all.

** Working on the stylesheet

Run the linter before you commit:

#+begin_src sh
  maak lint-css
#+end_src

It runs stylelint with =--fix= over =static/css/*.css=, using the rules in =.stylelintrc.yml=. The rule set is strict on purpose and checks, among other things, that no property, at-rule, pseudo-class or media feature is misspelled, that no declaration block repeats a property, that no selector is duplicated, and that specificity never descends within a rule block. A failure is a real defect, so fix the cause rather than disabling the rule.

There are two breakpoints. Below 600 pixels the bar wraps and scrolls away with the page; above 1100 pixels the sheet and the rail share the width. Everything else is one design that stretches, which is why the sizes are written as =clamp()= and the columns as =minmax()=: prefer a token or a clamp to a third breakpoint, and expect a reader on a laptop to see the same page as a reader on a desktop, only narrower.

* Client-side JavaScript

Four scripts ship with the site. They are plain, dependency-free JavaScript, and each has one job.

| Script                       | Loaded                        | What it does                                        |
|------------------------------+-------------------------------+-----------------------------------------------------|

| =static/js/symbanta.js=      | Every page                    | First-party analytics: page views, heartbeats and visibility changes |
| =static/js/guile-repl.js=    | Pages asking =#+SCRIPTS: repl= | The browser Lisp                                      |
| =static/js/tech-radar.js=    | Pages asking =#+SCRIPTS: radar= | The radar drawing, its legend and its keyboard-accessible controls |

Keep this property in mind when you add behaviour: a page downloads a script only if it asks for it, and a page that asks for nothing downloads only the two site-wide scripts.

** Analytics and privacy

The analytics script is first-party and deliberately modest. It registers three kinds of event: a page view, a heartbeat while the page stays visible, and a visibility change. Each event carries the page's own URL, the referrer, the browser's user-agent and language, the screen size, and a session identifier.

That identifier is generated in the browser and kept in the browser tab's session storage, so it is gone when the tab closes, and it is not a cookie, not shared between tabs, and not tied to any account. The script reports to the endpoint named in its =data-endpoint= attribute, defaulting to the project's own API host; it sends events with the browser's beacon API and falls back to a background request, and it fails silently when the network is unavailable. Removing the script tag from the page template switches the whole thing off.

* Metadata, feeds and crawlers

** Canonical URLs, robots and social cards

Every page declares one canonical URL, and the same string is used for the Open Graph and Twitter card, so a page never tells a search engine and a social platform different stories about where it lives. A forwarding page points its canonical URL at its destination and asks crawlers not to index the stub, which is how the two moved policies keep their old addresses working without competing with their new ones.

Every blog article gets a card of its own, composed while that article is being exported out of its title and its category, and written to =./public/og/<category>/<slug>.png=. The article's =og:image= and =twitter:image= point at it, so a shared link shows the article's own title rather than the site's tagline.

The cards are generated rather than drawn by hand for the same reason they can be trusted: a title is edited far more often than a card is redrawn, and a card that still shows the old title is a small lie about the page. The SVG the card was drawn from is kept beside its PNG, so a card can be read without a rasteriser, and a card whose SVG comes out identical is neither redrawn nor rewritten — an unchanged article costs a string comparison. Every card is the same size and uses the same design, so the set of them reads as one blog.

Only the blog articles get a card. An index, a landing page, a policy or a documentation page keeps =static/img/share-default.png=, which is the right description of a page whose subject is a whole section. That raster is the one image here that is not generated by the build; regenerate it from the SVG beside it when the design changes, rather than editing the raster:

#+begin_src sh
  maak share-card
#+end_src

That task exports the SVG with Inkscape and compresses the result with pngquant, both of which you must have available. It concerns the site-wide card only.

The type on a generated card is measured with the glyph advances of DejaVu Sans, which are declared in the build script because Emacs cannot measure a font in a batch build. Those advances decide how a title wraps and at which size it is set, so a title is laid out the way the rasteriser will draw it: no card overflows its own frame, and none is shrunk past legibility — a title that no size can hold is cut at a word boundary and marked with an ellipsis. Because a card is drawn during the build and not by a step of its own, a missing =rsvg-convert= does not fail the build: it reports how many cards it could not draw, and those pages keep the site-wide card rather than pointing a crawler at a file that is not there.

** Structured data

Each page embeds a JSON-LD graph that names the site and its author, then describes the page itself: a blog posting with its publication and modification dates for an article, a plain web page everywhere else, and a breadcrumb trail in both cases. The modification date is the author date of the last commit that touched the Org file, so it stays true without you maintaining it, and in a checkout without Git the field is left out rather than invented.

** The feed

=./public/rss.xml= is rebuilt on every publish from the published blog articles, with the title, the author, the description and the date of each one. The build forces a POSIX locale for this step so that the dates come out in the format the feed specification requires, which is one of those details that only shows up in someone else's feed reader.

A failure here is reported in the build log and does not abort the publish. The feed is a convenience, and half-published HTML would be worse than a stale feed.

** robots.txt and sitemap.xml

Both files are static and live in =static/=, copied into the output on every build. The robots file allows every crawler and points it at the sitemap. The sitemap lists the site's public addresses, including the sibling projects served from the same host, so it is maintained by hand and worth a look when you add a top-level page.

* Building the site

The whole publish is one command:

#+begin_src sh
  emacs -Q --batch -l ./jointhefreeworld-site.el --funcall jfw/publish
#+end_src

With Maak installed, the same work is wrapped with the housekeeping the project expects:

#+begin_src sh
  maak build
#+end_src

That task does three things the bare command does not:

- It deletes =./.org-cache=, the directory where Emacs records what it last exported, so a build starts from a known state instead of from whatever the previous one left behind.
- It empties =./public= before the export, so a file that no longer has a source cannot survive in the output.
- It copies =./static=, =robots.txt= and =sitemap.xml= beside the generated pages afterwards.

The batch invocation is not incidental. =maak build= runs Emacs through =guix time-machine= against the pinned channels in =channels.scm= and the manifest in =manifest.scm=, which is what makes the build reproducible. The tooling matters less than the property, though: the exporter itself is Emacs's own Org publishing machinery, so a build on any Emacs 29.1 or newer produces the same site.

** Where the output goes

Everything is written below =./public=, which is generated and ignored by Git. Never edit a file there; the next build overwrites it.

#+begin_example
  public/
    index.html                  the landing page
    404.html                    the not-found page
    rss.xml                     the feed
    robots.txt sitemap.xml      copied from static/
    blog/ documentation/ platform/ portfolio/   one directory per project
    code-of-conduct/ ai-policy/ the two site-wide policies
    og/                         one social card per blog article, beside the SVG it came from
    static/                     copied from ./static
#+end_example

** Local preview

To build and serve the result on the local port, run:

#+begin_src sh
  maak build-and-serve
#+end_src

The server is darkhttpd, serving =./public= on port 50011. The task first kills anything already listening on that port, so a stale server from an earlier session cannot shadow your build.

One consequence of the build's design is worth knowing before you test a change: because the development server reads straight from =./public= and the site's absolute URLs point at =http://localhost:50011=, every link, card and canonical URL in a development build addresses your own machine.

* Day-to-day work with Maak

[[https://codeberg.org/jjba23/maak][Maak]] is a command runner in Guile Scheme: a /Make/ with Lisp inside, pronounced to rhyme with the English word it descends from. Its tasks for this project are declared in =maak.scm=.

| Task                  | What it does                                                                 |
|-----------------------+------------------------------------------------------------------------------+
| =maak dev=            | Watches Org, Emacs Lisp, Scheme and CSS files and reruns the build and the server on every change |
| =maak hr=             | An alias for =dev=                                                             |
| =maak build=          | One production build into =./public=                                           |
| =maak serve=          | Serves the existing =./public= on port 50011                                   |
| =maak build-and-serve= | Builds, then serves                                                           |
| =maak fmt=            | Formats the Scheme and Emacs Lisp sources                                      |
| =maak lint-css=       | Runs stylelint with fixes over the stylesheet                                  |
| =maak lint-elisp=     | Loads the build script in batch mode, to catch a load-time error early         |
| =maak lint=           | Runs both linters                                                              |
| =maak test=           | Runs the ERT test suite for the build script                                   |
| =maak check=          | Runs every linter, then the tests                                              |
| =maak share-card=     | Regenerates the site-wide social card from its SVG                             |
| =maak deploy=         | Builds for production and copies the result to the deployment directory        |

=maak fmt= runs =guix style= over the Scheme files and indents the Emacs Lisp files, removing tabs and trailing whitespace. Run it before committing; it is the reason the sources look uniform.

=maak check= is the gate to run before pushing: it lints the stylesheet, loads the build script, and then runs the tests described below.

* Tests

The build is a program, and the tests treat it as one. =test/jointhefreeworld-site-test.el= is an ERT suite that loads =jointhefreeworld-site.el= itself rather than a copy of its rules, so a rule that changes shape in the build fails the suite instead of quietly disagreeing with a second copy of itself.

#+begin_src sh
  maak test
#+end_src

The suite needs no site build and writes nothing outside a temporary directory; a run takes well under a second once the Emacs packages the build installs are present. It covers:

| Area            | What is checked                                                                |
|-----------------+--------------------------------------------------------------------------------|
| URL layout      | That each publish project answers at the address its table entry promises, including the root, =/404.html= and the two top-level policies |
| Navigation      | That an article marks its own section rather than the whole blog, that the current entry is announced and not only coloured, and that every link is in exactly one of the bar's two groups |
| Page furniture  | The kicker that names a section, the stamp under a title that drops whatever the page does not have, and a generated page that carries the bar, the hero, the sheet and the rail |
| The rail        | That the rail is built from the page's own headings and anchors, that it needs three of them, and that a heading folded away in a closed disclosure is left out |
| Text and dates  | Tag stripping, entity decoding, word-boundary truncation, and that a bare date and a timestamp sort the same way |
| Listings        | That a category lists its own articles, that an unknown listing is empty rather than guessed, and that an entry escapes the title it is given |
| Social cards    | The wrap-and-balance arithmetic, that no line leaves the card, and that the SVG is well-formed XML |
| Structured data | That an article is a BlogPosting with its dates and section, that any other page is a WebPage, and that a title cannot close the script element |
| Tech radar      | That the article leads with the four rings in order, that each ring names layers from the known set, and that DeepSeek is trialled as a tool |
| Template        | That a generated page carries the document head, the chrome, the footer and the content, and that no placeholder survives |

Because the tests read the real content as well, they also catch a repository problem that has nothing to do with code: an article with no title, or with a date the build cannot read, fails the suite rather than the build log.

Nothing here replaces looking at the site. The tests prove that the pages say the right things; =maak build-and-serve= is still how you check that they look right.

* Deployment

Deployment is a copy. The site is served from =/srv/http/jointhefreeworld.org= by a static web server, and publishing means replacing the files there with a fresh build.

The build that runs for the live site differs in exactly one way: the =CI= environment variable. The build script chooses the absolute URL it writes into canonical links, cards and the feed based on it, using the real host when =CI=true= and the local address otherwise. That is why a development build's absolute URLs point at your own machine and a deployed build's do not.

=maak deploy= performs the copy in a careful order. It builds with =CI=true=, then removes the previously published =index.html=, =blog=, =portfolio=, =documentation/index.html= and =og= from the deployment directory before copying the new output over it. Those deletions exist so that pages and cards you removed from the sources do not linger on the server: a card is generated from the articles that exist today, so last year's card for a deleted article is exactly the kind of file that would survive a plain copy.

On [[https://codeberg.org/jjba23/jointhefreeworld][Codeberg]], a push to the =trunk= branch triggers continuous integration. The pipeline asks Byggsteg, the Guile Scheme build orchestrator, for a token, submits a job naming the =maak-deploy= task, and polls its status. The heavy work happens on the build host, not on the forge.

* Things that bite, and how to avoid them

** A page did not change after a build

The export is forced, so every page is written again on every build rather than skipped as unchanged; a page you did not touch simply comes out the same. What a build does remember is the cards: an article whose card SVG comes out identical keeps the PNG an earlier build drew, and an article whose title changed has its card redrawn and rasterised in that same build. If a build looks stale anyway, remove =./.org-cache= and build again, which is what =maak build= does for you.

** The wrong typeface is showing

The body and heading families are Lucida Sans first and Plus Jakarta Sans second, so the site keeps its character when Lucida is absent. The Lucida files are proprietary, are not distributed with this repository, and are served from =/static-assets/fonts= on the site's own host; the fallback is fetched from a font service. If the Lucida files are missing you get the fallback face, and nothing else breaks.

** A page asked for a script and nothing happened

Script names are matched exactly, and an unknown name is reported in the build log as =#+SCRIPTS: unknown script=. Read the log rather than the page: a typo is silent in the browser by design, so that a page never depends on a script that was not loaded.

** Analytics stopped reporting

The script validates its own configuration rather than trusting it: a missing or nonsensical heartbeat interval falls back to a default, and the session identifier is generated without assuming a secure context, so that a development server serving plain HTTP still works. If you change the payload, keep both behaviours, and remember that the script reports nothing and logs nothing when the endpoint refuses it.

** The feed is stale or missing

A feed failure is logged and swallowed on purpose. Look at the build output for =RSS feed build failed=, and check that the excluded pages are still where the build expects them.

** Something looks wrong in the footer

The footer prints the commit hash of the build, and the hash comes from the working tree at the moment of publishing. A footer that reads =unknown= means the build ran outside a Git repository, not that the build failed.

* Reproducible builds with GNU Guix

A build should never fail because it worked on your machine. Guix gives this project a declarative environment rather than a list of instructions that depend on what happens to be installed.

Enter the development environment with the pinned channels, then work as usual:

#+begin_src sh
  guix time-machine --channels=channels.scm -- shell -m manifest.scm
  maak dev
#+end_src

Four properties make this worth the trouble:

- *Pinned inputs.* =channels.scm= names one commit of Guix, so the environment is the same for everyone who asks for it.
- *Declared packages.* =manifest.scm= lists exactly what the build needs: Emacs without a window system, the development server, the file watcher and Texinfo.
- *Time travel.* =guix time-machine= can rebuild the exact environment of any point in the repository's history, which is how a build from a year ago can still be diagnosed.
- *Nothing global.* No part of the project installs into your profile or writes outside the repository, apart from the package directory the build creates for itself.
