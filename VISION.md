# Vision

jointhefreeworld is three things at once: a personal homepage, a blog, and the Emacs Lisp program that publishes both. The sources are Org files, the build is a library of `jfw-*` modules hanging off one entry point, and what leaves it is a directory of finished HTML, one RSS feed, a set of generated social cards and an SVG technical radar. The interesting question is not what the site says but what the build could become: a publication tool that derives every index from its own content and can prove it.

## Where jointhefreeworld is today

`jointhefreeworld-site.el` installs the packages and calls `jfw/publish`; the work is in eight modules under `lisp/`. `jfw-core.el` holds the site's constants — what it is called, where it lives, its colours, the fonts it preloads and the scripts a page may ask for. `jfw-pages.el` holds the URL layout and the publish projects. `jfw-ui.el` holds the header, the footer and the theme chooser. `jfw-blog.el` holds the article catalogue and every view over it: the listings, the archive, the keyword index, related reading, previous and next. `jfw-radar.el` draws the technical radar. `jfw-cards.el` draws the social cards. `jfw-jsonld.el` writes the structured data. `jfw-export.el` is the backend, the page template, the code blocks, the feed and the task entry point.

The build runs in four stages. `org-publish-all` exports every Org file below `./docs` to HTML below `./public` — forced, so nothing is skipped as unchanged — drawing each article's card while the article is in front of it, writing the blog's index pages out of the articles they list, and drawing the radar from the article that describes it. Each exported page then passes through a template that adds the head, the metadata, the JSON-LD and the chrome. The articles are collected into `rss.xml`. Finally `./static`, `robots.txt` and `sitemap.xml` are copied beside the output.

`maak build` is the same work with the housekeeping the project expects: it deletes `./.org-cache` so a build starts from a known state, empties `./public` so a file whose source is gone cannot survive, and copies the static tree back in afterwards. The batch invocation is not incidental — `maak build` runs Emacs through `guix time-machine` against the pinned channels, which is what makes the build reproducible, while the exporter itself being Org's own means any Emacs 29.1 or newer produces the same site. Deployment is a copy to `/srv/http/jointhefreeworld.org`, and the only difference between a local and a production build is the `CI` environment variable, which decides whether the absolute URL written into canonical links and cards is `localhost:50011` or the real host.

The URL layout is a convention rather than a mirror of the tree: an `index.org` answers at its own directory, any other file becomes a lowercased directory named after it, and `404.org` is the one file published as a plain HTML file because web servers look for that exact name. Links between Org files are rewritten to match, so you cross-reference by file name and the build produces the address. Moving a page between projects changes one table entry in `jfw-pages.el`, and every canonical URL, card and feed entry follows it.

Three things in the build are unusually good and worth understanding before criticising anything else. The **radar** is drawn at export time from the article's own headings — rings are first-level headings that ask for a `jfw-radar-ring` container, layers are the headings inside them, blips are list items — so the article stays the only source of truth, the picture is in the page a reader receives, and the geometry is ordinary functions ERT can state requirements about. The **cards** are drawn from the title and category during the export, with the glyph advances of DejaVu Sans declared in the build because Emacs cannot measure a font in batch, so a title wraps the way the rasteriser will draw it; a card whose SVG comes out identical is neither redrawn nor rewritten. And the **browser Lisp** is a real interpreter in plain JavaScript — reader, proper tail calls, closures, vectors, around a hundred primitives — that a page downloads only if it asks for it with `#+SCRIPTS: repl`.

The tests treat the build as a program: an ERT suite that loads `jointhefreeworld-site.el` itself rather than a copy of its rules, covering the URL layout, navigation, the page furniture, the rail, text and date handling, listings, card arithmetic, structured data, the radar's shape and the template. Because the tests read the real content as well, an article with no title or an unreadable date fails the suite rather than the build log.

That choice — the suite loads the real entry point — is worth more than it looks. It means a rule has one definition, and a change that breaks the rule fails a test instead of quietly disagreeing with a copy of itself. It is also why the gaps later in this document are specific rather than general: the suite is good enough that the remaining holes are places it structurally cannot see, not places nobody got around to.

The honest weaknesses are the ones the README admits in passing. `sitemap.xml` is maintained by hand, all 238 entries of it, including the sibling projects served from the same host. The build needs a network on first run, because it installs its Emacs packages into `./.packages`. `#+SCRIPTS:` knows exactly one script name. And the rule that a page's content never depends on a script is stated repeatedly and enforced nowhere.

The design half of the project deserves the same attention as the build half, because it is where the constraints actually live. One stylesheet, `static/css/jointhefreeworld.css`, organised entirely around custom properties — colour, type, spacing, shape, measure, frosting, glass, motion, paper — with two breakpoints and every size written as a `clamp()`. The glass is three cues on every pane (a lit top edge and shadowed bottom, a hairline brighter than the surface, a sheen from the corner nearest the light), and depth is two shadows rather than one. Blur is spent only where content moves under a surface, because a blur whose backdrop is fixed costs a repaint on every scroll frame and shows nothing.

The accessibility commitments are written as commitments rather than aspirations — contrast, focus, motion, transparency, structure — and several of them are enforced structurally: the first thing Tab reaches is a skip link, the current page is announced with `aria-current` rather than only coloured, the rail and the copy buttons are written by the build so they exist before any script, and the disclosure-based navigation is a real `<details>`. The one deliberate exception is the theme chooser, hidden until an inline script marks the document script-capable, because a control that could not remember a choice between two pages would be worse than none.

The navigation is data too: `jfw/nav-links` pairs a label with a site-relative path or an absolute URL, `jfw/nav-primary-paths` says which of them stay on the bar, and the tests check that every link ends up in exactly one of the two groups so a link cannot go missing between them. It is a small thing, and it is the pattern this document keeps arguing for: the facts live in a table, and a test reads the table.

## The vision

1. **One catalogue, every view.** `jfw-blog.el` already derives the listings, the archive, the keyword index, related reading and the neighbours from one set of articles. `sitemap.xml` is the exception, and it is the file most likely to lie: a page can be published and missing from it, or deleted and still listed. In a few years the sitemap, the feed, the JSON-LD graph and the `robots.txt` targets are all outputs of the same catalogue, and the sibling projects are declared in `jfw-core.el` where the rest of the site's constants live.
2. **The built site is checked, not only the build.** The ERT suite proves the functions say the right things; the README says plainly that nothing replaces looking at the site. The missing middle is a post-build pass over `./public`: every internal link resolves to a file that exists, every `og:image` points at a card that was drawn, no placeholder or `@@token@@` survives, every page has a title and a description, and no `#+SCRIPTS:` name was silently dropped.
3. **The no-script guarantee is a test rather than a principle.** It is the site's strongest claim and its most fragile: the rail, the listings, the copy buttons and every word of an article are in the HTML, and yet a single `<div id="app">` in a future template would break it quietly. A test that parses each built page, strips every script, and asserts the content is still there would turn a design intention into an enforced invariant.
4. **The build is hermetic.** Today the first build installs Emacs packages from MELPA into a directory of its own, which is the right instinct and the wrong dependency: a build that needs a network is not reproducible in the sense the project's own Guix arguments claim. A pinned, vendored set — with the versions named somewhere a test can read — would make `maak build` work on a machine with no network at all.
5. **Publication structure is data the build understands.** An article carries a title, a date, a description, keywords, a category and a highlight flag; everything else about how posts relate has to be expressed as a shared keyword, which related reading then weighs at three points. Series, collections, drafts and scheduled publication are not exotic needs for a blog with eighty-one articles and a technical stack page — they are the difference between a pile of posts and a publication.

Read as a group, statements 1 to 3 are the same claim three times: the build should be able to say what it produced and be held to it. That is the natural next step for a project whose catalogue is already a data structure and whose tests already read real content. Statements 4 and 5 are about the build's inputs rather than its outputs — one removes a network dependency, the other adds a concept — and they are the two that need a decision rather than a diff.

## Features that are in scope and not built yet

Each of these is a seam the build has already cut.

- **A generated sitemap.** `static/sitemap.xml` is copied verbatim on every build. *The hard part* is that it deliberately lists URLs this repository does not generate — the sibling projects on the same host — so the generator needs a declared list of external paths, and the `lastmod` values need a source of truth that is not a hand-typed date.
- **A build that needs no network.** The package install into `./.packages` is what makes the first build slow and fragile. *The hard part* is that pinning Emacs packages properly means either vendoring them or leaning on Guix, and the project's stated position is that a build on any Emacs 29.1 will do.
- **A second page script.** `#+SCRIPTS:` accepts a comma-separated list and reports an unknown name in the build log, which is the right shape for a typo. *The hard part* is that each script is a page-level decision with its own guard, and the set is currently one, so the multi-script path is untested.
- **Card drawing without a rasteriser.** A missing `rsvg-convert` does not fail the build: it reports how many cards it could not draw and those pages keep the site-wide card. *The hard part* is that drawing text into SVG requires the font metrics the build already declares, so the PNG is a convenience rather than a necessity — but a social platform will not accept an SVG.
- **Analytics the site does not see.** `symbanta.js` reports page views, heartbeats and visibility changes to a first-party endpoint, with a session-scoped identifier in `sessionStorage`. *The hard part* is that the reading side lives in another repository, so this project cannot tell you its own most-read pages, and any attempt to put them on the site raises the question of whether popularity should shape a homepage.
- **A search, given the philosophy.** The keyword index and the archive answer two questions well. *The hard part* is that full-text search on a static site means either a build-time index and a script, or one page per word — and the second is absurd for a corpus this size while the first contradicts statement 3.
- **Translations.** The site is English, with an `#+LANGUAGE: en` on the README and nothing on the pages that would say otherwise. *The hard part* is that a translated blog is two catalogues, two feeds and a canonical-URL policy, not a `#+LANG:` keyword.
- **The rail's three-heading threshold.** The rail takes a column only above 1100 pixels and only when the page has at least three headings, which is a good rule and a hard-coded one. *The hard part* is that it is a layout decision expressed in the build rather than the stylesheet, so a designer cannot change it without reading Emacs Lisp.
- **The 404 page's links.** `docs/home/404.org` is a page like any other, so its suggestions are maintained by hand. *The hard part* is that the useful 404 needs the catalogue — the recent articles, the categories, the keyword cloud — and the page that serves it is the one page the build cannot route through its own template path in the ordinary way.
- **A moved-article record.** `#+REDIRECT:` gives a stub a refresh, a canonical URL pointing at the destination and a request not to be indexed, which is how the two moved policies keep their old addresses. *The hard part* is that a redirect is a page a human has to create, so the catalogue cannot tell you that an article was renamed and a link is now dead.
- **The analytics endpoint's contract.** `symbanta.js` posts to the endpoint named in its `data-endpoint` attribute, defaults to the project's own host, and fails silently when the network is unavailable. *The hard part* is that the shape it posts is defined by another project, so the compatibility surface is invisible from this repository.
- **Sibling projects on the same host.** The sitemap lists pages this repository does not generate, and the footer links the source host and the professional profile from tables in `jfw-core.el`. *The hard part* is that a shared host makes the "site" boundary porous, so any generator has to be told what else is on it.

## New features that would be worth having

- **A series model.** `(name . "part 3 of 5")` on an article, a series index generated from the members, previous/next that follows the series rather than the blog's chronology, and a JSON-LD `isPartOf`. The pieces are all in `jfw-blog.el` already: it knows how to find neighbours and how to weigh a shared keyword, and a series is the explicit version of the relationship that keywords can only approximate.
- **A "what changed" page.** The build already reads git for two things — the footer's short hash and each Org file's last-commit date. A page listing the articles modified in the last ninety days, derived from the same `git log` the JSON-LD modification dates come from, would be a cheap and genuinely useful view. *(Speculative in value: it is more interesting on a documentation site than on a blog.)*
- **A per-category feed.** `rss.xml` carries every article. A feed per category is a `webfeeder` call per listing, and the catalogue already knows the categories. *Why it is worth having:* somebody who reads only the Emacs posts should not have to filter the feed themselves.
- **A "reading list" page from the data the site already keeps.** The blog index and two category pages keep a short `Elsewhere` list by hand. *Why it is worth having:* a link with a date, a title and a one-line reason is exactly the shape an article entry already has, so a link is almost an article with an external URL — and the current arrangement is the only content on the site that is not derived from anything.
- **Generated cards for the non-article pages.** Only articles get a card; an index, a landing page or a policy keeps the site-wide raster. Since the card builder already takes a title and a label, the work is in deciding whether a section page's card should say something different. *(Speculative.)*
- **A print stylesheet for articles.** The design is a screen design with two measures — 80 characters of prose, 128 of code — and a long technical article is exactly the thing somebody prints or saves as PDF. *(Speculative: nobody has asked, and the answer may be "the browser's reader mode is better than anything I would write".)*
- **A draft state.** An article that exists in the repository but is not published, without deleting it from `docs/`. *Why it is worth having:* writing in public is a decision, and the current model forces it at the moment the file exists. *(Speculative in mechanism: the obvious implementation is a `#+DRAFT:` keyword the export honours, which is a small change with a large temptation to leak.)*
- **A webmention or comment path.** The site has no discussion at all, and an article about `SQL SELECT *` or a technical radar is the sort of thing people reply to. *(Speculative, and quite possibly wrong: an inbox is a maintenance burden, and the site's dignity is partly that it does not have one.)*
- **A regression corpus of built pages.** The ERT suite reads the sources; a saved copy of one built page per project, diffed on every run, would catch a template change that nobody meant. *(Speculative in discipline: a fixture regenerated whenever it fails is worse than none, and the site's own tests are already unusually good at reading real content.)*
- **An article about the build.** The radar's move from a browser script to build time is documented in a module commentary and nowhere a reader would find it. *Why it is worth having:* it is the project's best argument, it is already half-written in `jfw-radar.el`, and it belongs on the site rather than in the source.

## Contributions that would move the needle

1. **A generated sitemap from the catalogue.** The catalogue already knows every article; the missing part is the list of external paths and a `lastmod` source. *Why it is a good task:* it removes the file most likely to be wrong on a site whose whole argument is that derived things cannot drift, and it is a contained change in `jfw-pages.el` with a spec that would have caught the existing staleness.
2. **A post-build link check.** Walk `./public`, resolve every `href` and `src` that is site-relative, and fail on a miss. *Why it is a good task:* it is the cheapest possible version of statement 2, it needs no Emacs package, and it would have caught whatever is currently broken.
3. **The no-script assertion.** Strip the scripts from each built page and assert the heading, the article body and the listing survive. *Why it is a good task:* it is one ERT test over the real output and it protects the site's central claim, which is currently protected by care.
4. **Pin the package set.** Name the versions `use-package` installs, and make a build without them fail with a message that says what to install rather than fetching it. *Why it is a good task:* it turns "the first build needs a network" from a documented caveat into a solved problem, and it makes the Guix section of the README honest.
5. **A series, end to end.** One keyword, the index, the navigation, the JSON-LD. *Why it is a good task:* it is the first relationship the build understands that is not implicit, so it is the change that decides whether the catalogue is a data structure or a set of conventions.
6. **One more article.** This is a blog with eighty-one of them and its best documentation is a post that solves a real problem. *Why it is ranked last and is not really last:* writing is the contribution this project is actually for.
7. **A `#+SCRIPTS:` line that names something new.** The multi-script path exists and has one user. *Why it is a good task:* it is the cheapest way to find out whether a page-level script decision is a real mechanism or a coincidence, and a new script has to justify itself against the no-script guarantee, which is a useful argument to have.

The ranking is value per hour, and the top two are hours rather than days. A generated sitemap and a link check are the two changes that would most reduce the chance of the site being quietly wrong, which is the failure mode a static site has: nothing crashes, something is just missing from an index nobody looks at. What is deliberately not on the list is a redesign. The design is coherent, the tokens are in place and the commitments are written down; a redesign would be a lot of work that teaches nothing about the build.

## Compared to related projects

| Project | What it is | Where jointhefreeworld differs |
|---|---|---|
| Org's own `ox-html` and `org-publish` | The exporter and publishing machinery this build is made of | jointhefreeworld is a layer on top, not a competitor: it adds the URL layout, the template, the catalogue, the cards, the radar, the feed and the tests, and leaves the Org semantics to Org. |
| `org-static-blog` | A small, popular Emacs Lisp blog generator from Org files | The closest neighbour, and the same idea with far less: a post list, a feed, tags. It has none of the derived views, none of the build-time drawing and no ERT suite that reads the content. |
| Hugo | A fast Go static site generator with taxonomies, sitemaps and themes | Hugo generates the sitemap from content and has a template language for everything else. jointhefreeworld has a Lisp instead of a template language, which is why the radar and the cards can be *drawn* rather than templated. |
| Jekyll and Eleventy | Ruby and JavaScript static site generators with collections and data cascades | Both have a genuine content model — collections, front matter, a data cascade — that this build approximates with categories and keywords. Neither draws its own artwork at build time. |
| Zola | A single-binary Rust generator with taxonomies, a sitemap and a built-in search index | The closest comparison for the *output*: Zola ships a search index and a sitemap generator that this project does not. What it does not do is treat the source document as the only copy of a chart's geometry. |
| Haunt | A static site generator written in Guile Scheme | The same instinct in a different Lisp: a build you can read. Scheme is the better language for the job; Emacs Lisp is the only one that already contains Org, and Org is the reason this build exists. |
| Astro | A component framework that emits mostly-static HTML with islands | The modern, well-funded answer to the same problem. jointhefreeworld has no build tool, no bundler and no dependencies beyond Emacs packages, and its "islands" are one script a page opts into. |
| Neocities-era hand-written HTML sites | The thing a static site generator replaces | Worth remembering as the baseline: the output here is a directory of files that any web server can hand over, which is the one property that survives every framework cycle. |
| Ghost and self-hosted WordPress | A database-backed publishing system with an editor, themes and a feed | They solve the writing experience, which this build does not attempt: no admin UI, no scheduling, no drafts. What they cost is a daemon, a database and a patching obligation, which is precisely what a directory of files avoids. |
| Pandoc with a template | A converter that will render Markdown or Org to HTML with a template you write | A converter, not a publication: no catalogue, no listings, no cards, no radar, no feed, no tests over the output. It is a good tool for producing one page and a poor one for maintaining eighty-one of them. |

What the others do that jointhefreeworld could still add: Hugo and Zola generate their sitemaps and, in Zola's case, a search index, and there is no good argument for hand-maintaining either. Both also treat taxonomies as first-class data, which is the gap between a `#+KEYWORDS:` line and a series. Jekyll's collections and Eleventy's data cascade are the mature versions of the catalogue this build already has half of.

Where jointhefreeworld is ahead and should stay ahead: the radar. A chart whose geometry is derived from the prose that describes it, drawn before the page is served, with ERT stating requirements about the bands and the labels, is a genuinely unusual and correct arrangement — and the alternative, a browser script reading the DOM, is what it replaced. The cards are the second example of the same discipline. The third is the browser Lisp: shipping a real interpreter to a page that asks for it, with everything it evaluates staying in the tab, is a better answer to "interactive" than a framework bundle.

The comparison that matters most is not with a generator at all but with the hosted platforms — Medium, Substack, a Notion page. They win on everything except the two properties this project is built on: the address is yours, and the artefact is a directory of files that any web server can hand over. Those two are worth more every year, and they are worth stating plainly because they are the reason the awkward parts of this build — Emacs Lisp, Org, a hand-written sitemap — are worth tolerating rather than replacing with something trendier.

## In the long run

The long bet is that the document is the artefact and the site is a view of it. Everything that is derived here — the URL, the card, the feed entry, the JSON-LD, the radar, the related reading — is derived from one Org file, and the project's most interesting failures are the places where that is not quite true yet. A build that derives everything and can check it is not just a nicer blog: it is an argument that a publication can be a program.

The second bet is about Emacs. Org is the best structured-prose format anybody has shipped, and Emacs is the only environment that already contains it, which is why this build is Emacs Lisp rather than Scheme like its siblings. That is a constraint, not a preference — and it is worth being clear-eyed that it limits who can contribute, which is why the tests and the modules are written the way they are: a build a reader can follow is the mitigation.

The bet has a price worth naming: the modules are Emacs Lisp, so a reader who knows Org but not Emacs Lisp can publish by writing Org and cannot fix the build. Every mitigation — the module split by subject, the docstrings, the ERT suite that loads the real entry point, the constant tables in `jfw-core.el` — is an attempt to keep that price payable. If the project ever gains a second regular contributor, this is the section that will have been right or wrong.

The third bet is that a personal site should be small. Three scripts, one stylesheet, one directory of files, a server that does nothing but hand them over. Every framework generation adds a reason to give that up, and the site's own answer — that the content is in the first byte and the scripts are comfort — is the thing worth carrying forward even when the tooling around it changes.

What would falsify these bets: if Org's own export machinery changes shape, the build's foundation moves under it, and the modules are deliberately thin enough that the port would be days rather than months. If Emacs 29's publishing API is eventually deprecated in favour of something else, the same applies to a smaller degree. And if the web's crawlers stop trusting hand-rolled JSON-LD and RSS in favour of feeds and protocols the site does not speak, then some of the derived metadata becomes decoration — which would leave the radar, the cards and the documents, and those would still be worth the build.

## How to read this document

The in-scope list names things the build has already half-committed to; the rest are proposals, and the speculative ones are marked because they may well be wrong. Nothing here is a plan with dates, and the sitemap could honestly be generated by lunchtime.

The useful way to read the five statements is as one question: can the build be held to what it produced? A sitemap that is generated, a link that is checked, a page that survives its scripts being removed — those three are the same discipline applied at three scales, and none of them needs a new concept. The two that do need one — a hermetic build and a series model — are the two worth arguing about in an issue before anybody writes code.

*This document describes intent, not commitments; the build, its ERT suite and the published site remain the only account of what jointhefreeworld does.*
