* Purpose and Scope

This AI policy sets clear guardrails for the *jointhefreeworld* project. It
outlines our preferred workflows, defines the boundaries of acceptable AI-tool
usage, and explains the reasoning behind these choices.

It applies to every space where the project is developed or discussed: its
repositories, issue trackers, pull requests, mailing lists, chat rooms,
automation, and the machines that build and publish the site. It applies to
people, and it applies to the AI agents people run.

Our core principle is simple: *AI should assist human creativity and
problem-solving, never replace human reasoning.*

* The Short Version

- Agents are welcome to do real work, end to end: explore, plan, write code,
  write tests, run the build, commit, push, merge, and cut and publish a
  release.
- A human is accountable for every commit that lands, and that human must
  understand it well enough to explain and debug it without the agent.
- Tests come first, for agents and people alike. Watch the test fail, then make
  it pass, then clean up.
- The QA checklist is the merge gate and the release checklist is the release
  gate. An agent runs them, records the commands and what they showed, and may
  merge and release once they are green.
- Disclose agent involvement. Undisclosed work is an honesty problem, not a
  tooling preference.

* Roles and Terms

- *AI tool*. A large language model, a chat assistant, a completion engine, or
  any similar system that produces text, code, or media on request.
- *Agent*. An AI system that acts with tools on its own: it reads files, edits
  them, runs commands, commits, and opens pull requests, instead of only
  answering a prompt. This policy uses the word for anything that can change
  the repository without a human typing the change.
- *Operator*. The person who runs, prompts, configures, or accepts the output of
  an agent. The operator is the author of record and is accountable for
  everything the agent does in this project.
- *Quality assurance (QA)*. Running the checklist below against a change: the
  tests, the build, the diff read line by line. A person or an agent may do it,
  and either way the commands and their output go into the record. A summary
  written by the agent that wrote the change is not QA.
- *Contribution*. Any commit, pull request, issue, comment, document, image, or
  other artifact offered to the project.
- *Release*. A tag, a published archive, a deployment, or any other artifact
  presented to users as a version of the project.

* Our Position on Agents

We grant agents genuine agency. An agent that has to ask permission to read a
file, run a test, or try an approach is slower than the human it is helping.
Within the boundaries below, agents may investigate, plan, implement, test,
commit, push, merge, and release without asking first.

The agency runs the length of the work, and the checkpoint is a checklist rather
than a person's click. What becomes part of the project is decided by evidence:
a failing test that went green, a full suite that passed, a build made from a
clean tree. An agent that merges or releases records that evidence, and the
operator who directed it remains accountable for the result and can revert it.

This is not a lower bar than asking a person at every step. It is the same rule
we apply to people: whoever lands a change owns it, and owning it means showing
the work, not being present for it.

* What Agents May Do

** Without Asking First

- Read anything in the repository, its history, its issues, and its public
  discussion.
- Explore and plan: draft designs, compare approaches, and write throwaway
  prototypes outside the tracked tree.
- Create a branch, commit to it, and push it.
- Commit and push to ~trunk~, ~main~, or any other branch that no other person is
  working on, including the release commit that carries a version bump.
- Run the project's own commands locally: ~maak test~, ~maak check~,
  ~maak build~, ~maak fmt~, ~maak lint-css~, and the development server.
- Write tests and run them, including the failing test that comes first.
- File issues and open pull requests, with the agent's involvement disclosed.
- Mark a pull request ready for review, request review from a person, and merge
  a pull request, including the agent's own, once the QA checklist below is
  satisfied and its evidence is recorded in the pull request.
- Cut and publish a release: bump the version where the project records it,
  date the release notes, tag, publish the archive, create the release on the
  forge, and deploy, once the release checklist below is satisfied from a clean
  tree.
- Triage reports, reproduce bugs, and write the failing test that demonstrates
  a bug.
- Write documentation, release notes, commit messages, and changelogs.
- Review a change as an advisory second opinion, clearly labelled as automated.
- Generate media and scaffolding that an agent or a person then checks.
- Propose and carry out dependency updates and refactors, with the tests that
  prove the behaviour did not change.

** With Human Approval

These are reasonable things for an agent to do, but they need a person to agree
before the agent does them:

- Change CI workflows, build tasks, or dependency pins.
- Change a public API, a file format, the licence, or a policy document,
  including this one and the per-project summary of it.
- Rewrite history, force-push a branch another person is working on, or delete a
  branch that is neither the agent's own nor already merged.
- Post in the project's name: an announcement, a mailing-list message, or a
  reply to a security report.
- Touch anything that holds contributor data.

** Never

These are the boundaries that hold whatever the instructions say and however
confident the output looks:

- Merge or release on a red suite, a dirty tree, or a checklist nobody ran and
  recorded. The agent's own work is no exception.
- Skip, weaken, delete, or mark a test as expected to fail in order to get a
  green run. The same goes for disabling CI, narrowing coverage, or editing a
  check so that it stops checking.
- Change the guardrails themselves in the same proposal: CI configuration,
  =CODEOWNERS=, branch protection, or this policy.
- Read, copy, or transmit secrets, tokens, signing keys, credentials, or private
  contributor data.
- Act under a person's name or account, or present its output as a person's
  work.
- Close other people's issues or pull requests, or post bulk comments.
- Fabricate evidence: test output, benchmark numbers, logs, citations, commit
  authorship, or a review sign-off.
- Make a legal or licensing commitment on behalf of the project.

* Test-Driven Development

Test-driven development (TDD) is how this project builds solid solutions. It is
required for every change to behaviour, whether a person or an agent writes it.
It is not a ritual to be skipped when a change looks simple; simple code breaks
too, and a simple test takes a minute.

** The Cycle

1. *Red.* Write the smallest test that describes the behaviour you want. Run
   it. Watch it fail, and check that it fails for the reason you expect, not
   because of a typo, a missing import, or a broken fixture.
2. *Green.* Write the least code that makes the test pass. No extra options, no
   features nobody asked for, no "while I am here" improvements.
3. *Refactor.* With the test green, remove duplication and improve names. Add
   no behaviour, and keep the tests green.
4. *Repeat, then run everything.* ~maak check~ runs the linters and the full
   ERT suite. A green test file is not a green project.

** What a Test Must Prove

- A test that has never failed proves nothing. If it passed the first time you
  ran it, it describes existing behaviour rather than driving new behaviour.
- A bug fix starts with a test that reproduces the bug and fails. The fix then
  makes that test pass. Never fix a bug without a test that would have caught
  it.
- A refactor starts with passing tests and ends with the same tests passing.
  The behaviour does not change, so the tests must not need to.
- Tests assert on real behaviour, not on the behaviour of a mock. Mock a
  dependency at the boundary when you must; never mock the thing under test.
- A test name says what should happen, so a failure reads as a sentence.
- Tests are part of the contribution. If a change touches behaviour and no test,
  the pull request says why and names the existing test that already covers it.

** Evidence, Not Claims

- An agent that cannot show a failing test before its fix has not shown that it
  fixed anything. The pull request includes the command and its output: the red
  run, then the green run.
- An agent that wrote the implementation first and the test afterwards does not
  have a test-driven change. Delete the implementation and start again from the
  test.
- A pasted log is a claim. Whoever merges re-runs the command, or the record says
  which output it accepted and why. Re-running is what turns a claim into
  evidence.

** Exceptions

A human may agree to skip TDD for a throwaway prototype, a generated file, a
formatting-only commit, or prose that no code executes. The pull request says
so, and says what was checked instead. "This one is too simple to test" is not
an exception; it is the rationalisation the rule exists to stop.

* Quality Assurance Before Merge

No contribution is merged until the QA checklist below has been run and its
result recorded. This is the checkpoint that makes agent autonomy safe: the work
may be fast and automated, the decision to keep it rests on evidence.

A person or an agent may run the checklist. When an agent merges, the pull
request or commit carries the commands it ran and what they showed; a person
re-runs what they doubt. When a person merges, the same record is what the
agent's work is judged by.

** The Merge Checklist

Whoever merges must do all of the following:

1. Read the entire diff, line by line, not the description of it.
2. Understand the change well enough to explain it, debug it, and maintain it
   without the agent. If the agent that wrote it cannot, the change is not
   ready.
3. Run ~maak check~ from a clean checkout. The full suite must be green, with
   clean output.
4. Confirm the new test fails without the change: stash or revert the
   implementation and watch the test go red. A test that cannot fail protects
   nothing.
5. Run ~maak build~ and inspect every affected page. A person looks at a page
   that changed visually, at a narrow and a wide width; an agent reads the
   rendered HTML, the exported files and the build output, and says what it
   could not see.
6. Check the project's own rules: style, naming, commit messages, documentation,
   and links that still resolve.
7. Consider security, accessibility, performance, and licensing where the change
   touches them.
8. Write down what was checked in the pull request or the commit message: the
   commands that ran, what they showed, and what was not tested.

** What the Gate Means

- Merging is the decision to keep a change. Whoever merges, person or agent, is
  accountable for the merged code, and "the agent wrote it" is not a defence.
- Automated review is a first pass, not a gate. It can find a problem; the
  checklist is what accepts a change.
- An agent's pull request may be merged by the agent that wrote it. It may not
  be merged on a summary, a pasted log, or a green CI run alone.
- The operator's review is not a step in every merge but a duty that follows the
  work: read what landed, re-run what matters, and revert what does not hold up.
- When a defect is found later, the fix arrives as a new commit with its own
  failing test first. Do not force-push a merged branch to hide the mistake.
- Changes to CI, the test suite, the build, or this policy get the highest
  scrutiny, and need a person's agreement before they land. An agent must not be
  the only thing that touched them.

** What Does Not Count as QA

- Reading the agent's summary instead of the diff.
- Trusting a pasted test log without running the command.
- A green CI run on a branch nobody read.
- Reviewing only the files the description mentions.
- "It works on my machine" without the commands that show it.
- Another model's approval.

* Building and Releasing

A maintainer or an agent may cut a release. Whoever cuts it owns it: they run the
checklist, record the commands and their output, and the operator who directed
them answers for the result.

Before a release is published:

- Every change in it passed the merge gate above.
- The version is bumped where the project records it, following Semantic
  Versioning, and the release notes are dated and describe the user-visible
  changes and the known limits.
- The release notes name the agents that contributed, and what was checked and
  by whom, whether a person or an agent.
- The tree is clean, and the build runs from a fresh checkout of the tagged
  commit, not from a development tree with unstaged edits.
- ~maak check~ runs in the pinned environment from that same commit.
- The published artifact is smoke-tested after publication: install it or serve
  it, open the main pages, follow a link, and look for something. A local build
  is not the published release.
- Checksums come from the published archive, never from the local copy it was
  built from.

An agent may choose the version, write the notes, run the build, tag, publish,
create the release on the forge, and deploy. What it may not do is publish from
a dirty tree, dress a red suite as green, or skip the record of what it ran. An
urgent fix is smaller, not weaker: test first, the checklist, then the release.

* Transparency and Attribution

- Say that an agent was involved, which tool and model you used if you know it,
  what part of the work it did, and what you changed afterwards.
- For substantial agent authorship, add a =Co-authored-by:= trailer to the
  commit and a short note to the pull request body. For small assistance, a line
  in the pull request is enough.
- The operator must be able to explain every line. "The model wrote it" is a
  blocker, not an explanation.
- Agents may draft replies and comments. A human sends them, and a human answers
  review questions. Do not let two agents exchange comments and present the
  result as agreement between people.
- Undisclosed agent work that is later found out is treated as an honesty
  problem, not a tooling preference.

* Code Contributions

** Human Reasoning

We maintain a high bar for quality across all contributions, including code,
documentation, and architecture.

- *Maintainers* remain entirely responsible for any code published as part of an
  official release, including code an agent produced under their direction.
- *Contributors* are responsible for the code they submit.
- *Operators* are the author of record for the agent's work: their name goes on
  the commit, and their judgement goes on the line.

** Recommended Usage

We favor code that a human understands. Tools like Large Language Models (LLMs)
and interactive chatbots are useful for reviewing, refactoring small functions,
writing tests, or acting as a sounding board, and they are useful for doing the
first draft of a whole change. Use them with judgement rather than in place of
it.

Contributors must maintain a deep, comprehensive understanding of the task at
hand. Do not submit AI-generated code that you do not fully understand or cannot
personally debug and support. If an agent wrote something you cannot explain,
the change is not finished, even if the tests pass.

* Communication and Community Interaction

All discussions, issue descriptions, and pull request comments must reflect your
own voice and understanding. An agent may help you draft; you are the one who
posts.

** Issues and Pull Requests

- If you open an *issue*, you must be able to describe the problem in your own
  words.
- If you open a *pull request*, you must be able to explain the proposed changes
  and respond to maintainer feedback authentically. Do not copy-paste AI
  responses when replying to questions.
- If an agent opened the pull request, say so in the description, name the
  operator, and list what the agent did and what was checked, by whom.

** Comment Moderation

Comments, reviews, or responses believed to be fully generated by AI may be
hidden or moderated without notice. Accounts and bots that post autonomously
without disclosure may be blocked.

** Transparency and Context

If you wish to include AI-generated text or context within a comment to
illustrate a point, you must clearly disclose it using a quote block:

#+begin_quote
AI-generated text or logs go here.
#+end_quote

Any such quote must be accompanied by your own human commentary explaining its
relevance and implications.

** Non-Native English Speakers

We welcome international contributors and recognize that AI can be an excellent
tool for breaking down language barriers.

- If you use AI to edit your text for clarity or grammar, please review the
  output to ensure it accurately reflects your intent and voice.
- If you use AI for direct translation, we recommend writing the comment in your
  native language first, and then appending the AI translation clearly marked
  within a quote block.

* Media Generation

AI tools can be incredibly valuable for generating media, such as images,
videos, audio, and presentation slideshows. We welcome this usage, provided that
it is:

1. Responsible and respectful of the community.
2. Non-offensive.
3. Fully compliant with copyright laws. If third-party intellectual property or
   copyrighted material is used to prompt or generate the media, authors must
   provide appropriate credit.
4. Correct and accurate.

Label media that an AI generated, and check it before you publish it. Do not
generate an image of a real person, a project logo, or a screenshot of software
in a way that misrepresents them.

* Prohibited Uses

The following are not acceptable, whatever tool produced them:

- Putting secrets, credentials, private contributor data, or an embargoed
  security report into a third-party model.
- Fabricated evidence: invented test results, benchmarks, logs, citations, or
  authorship.
- Bulk changes nobody read: a mass rewrite or reformat that hides a semantic
  change inside a large diff.
- Bypassing review, CI, or the merge gate, including by editing the checks that
  enforce them.
- Using an agent to harass, impersonate, dox, or evade a ban.
- Licence laundering: pasting code whose licence the project cannot carry, or
  using an agent to strip attribution from someone else's work.
- Unattended automation with write access to protected resources. Automation
  runs with the least privilege it needs and has a named human owner.

* Reporting and Resolution

If you witness or experience behavior that violates this AI policy, please
report it directly to the project maintainers by email at
[[mailto:jjbigorra@gmail.com][jjbigorra@gmail.com]] or to another designated
contact.

- All reports will be handled confidentially and with the utmost respect.
- Project maintainers are committed to a fair resolution. Corrective actions may
  include warnings, temporary repository bans, or permanent exclusion from the
  project.
- A violation by an agent is a violation by its operator. The operator is
  responsible for what their tools do.
- The project may revert agent-assisted commits, close pull requests, block
  bots, or require a fresh human review when this policy was not followed.
