#+KEYWORDS: Org-mode, Guile Scheme, PEG, parsing, performance, profiling, benchmarks, free software

OrgWebAlchemy is a library for GNU Guile that parses Org mode documents with a Parsing Expression Grammar and renders them to HTML, Markdown, or SXML. In an [[https://jointhefreeworld.org/blog/articles/lisps/parsing-expression-grammar-lisp-org-convert-to-html/][earlier article]] I explained why I believe a PEG is the right tool for Org: the grammar describes the language, the parser produces a tree, and the renderers turn that tree into output.

This article is about the work that came after that, and about a question that turned out to be more interesting than I expected. How do you make such a program fast without making it wrong? I did not want a parser that is quick on the documents I happen to test and quietly different on the documents you write.

So I will describe the features that were added, the way I measured the work, the profile that told me where the time went, the two rounds of changes that followed, and the verification that lets me claim the language did not change. I will report the numbers I measured and I will tell you how to repeat the measurements yourself. That last part is not a courtesy. A number you cannot check is not evidence; it is advertising.

Here is the whole article in five sentences:

- Parsing a 58 KB Org document now takes 5.1 ms, where it used to take 32.2 ms, a factor of 6.4.
- The same parse now allocates 3.9 MB, where it used to allocate 30.3 MB, which is 7.8 times less garbage.
- A document consisting of one 80 KB line went from 8.2 seconds to 0.37 milliseconds, because the old path was quadratic in the length of a line and the new one is linear.
- The library gained a Markdown renderer, figures, named elements, cross-references, a proper table reader and mixed nested lists, and it says plainly what it still does not do.
- None of this was guessed: there are 155 test definitions and 281 assertions, an equivalence run compared the new parser with the previous one on 70,858 inputs, and a test sweeps 391,094 positions to check the scanner's stop set.

Before the numbers, a word about why the shape of the program matters as much as its speed.

* Free software, and why this is a library

OrgWebAlchemy is free software, released under the GNU Lesser General Public License, version 3 or later, with this documentation under the GNU Free Documentation License. That means you may run it, study it, change it, and redistribute your changed versions. It also means the program belongs to its users, not to me.

This could have been written differently. It could have been a service: you send your Org file to a server, a program you do not control turns it into HTML, and you get the result back. Such a service can be convenient, and it can even be gratis, but it leaves you helpless in the ways that matter. You cannot study it, you cannot fix it, and you cannot keep using it when the operator loses interest or changes the terms. I wrote a library instead, because a library goes into your program, on your machine, under your control.

The Lesser GPL is a compromise, and I should name it as one. The GNU General Public License would keep every program that uses this code free as well, and that is the stronger guarantee for users. For libraries, the GNU Project has long accepted a weaker license so that more programs can use them, including some that are not free, and I have followed that tradition here. If you use this library in a free program, you are helping the community. If you use it in a nonfree program, I would rather you made that program free.

There is a second reason the library is a library. Org mode is a language, and a language is useful in proportion to the number of programs that can read it. A parser that only Emacs can use is a parser for one program. A parser that any Guile program can call is a parser for a text editor, a static site generator, a wiki, a notebook, a mail archiver, a package's documentation build, or a program that nobody has written yet. I do not know what you will build with it, and that is the point.

Perhaps I should also say what this program is not. It is not Emacs, and it does not try to be. Emacs is where Org mode lives, where it is edited, and where its export machinery began. OrgWebAlchemy does not replace that; it lets other programs, written in Scheme, read the same documents. When it disagrees with Emacs about some corner of the syntax, Emacs is right and this library has a bug.

OrgWebAlchemy is still three small modules. What changed is how much of the language each one covers.

The application programming interface is still small enough to hold in your head.

#+begin_src scheme
(use-modules (orgwebalchemy html)
             (orgwebalchemy markdown)
             (orgwebalchemy peg))

(org->html "This is ~test~ code.")
;; => "This is <code>test</code> code."

(org->markdown "This is ~test~ code.")
;; => "This is `test` code."

(define ast (org->ast "* Hello\nA *bold* line.\n"))
(org-ast->html ast)
(org-ast->markdown ast)
#+end_src

Everything else in this article is about what happens between those two calls.

* Teaching the parser more of Org

"Supporting Org" is a phrase that hides a great deal of work, because Org is not a markup language with a tidy grammar. It is a set of conventions accumulated over many years of a GNU Emacs major mode, some of them deliberately informal, and each one has to be considered on its own terms. Every feature below began as a sentence in the Org manual, became a pattern in the grammar, and then became a test.

** Links: decide once, in the parser

An Org link is not a uniform resource locator in brackets. Its target says what kind of link it is. A target beginning with ~https://~ is external. ~file:photo.png~ is a file, and so is a bare ~notes.org~. ~#custom-id~ points inside the document. ~*Heading~ points at a heading. A ~::search~ suffix says where inside the target you land.

The old code let each renderer read the target and decide again for itself. That is exactly how two back ends drift apart. The HTML renderer grows a special case for image extensions, the Markdown renderer grows a slightly different one, and after a year of small repairs the same document has two meanings depending on which function you call. A user who notices will not know which one is correct, and will be right to distrust both.

So classification moved into the parser, where it happens once.

#+begin_src scheme
(org-link-parts "https://example.org/a")   ;; => (https . "//example.org/a")
(org-link-parts "file:photo.png")          ;; => (file . "photo.png")
(org-link-parts "notes.org")               ;; => (file . "notes.org")
(org-link-parts "#custom-id")              ;; => (internal . "custom-id")
(org-link-parts "*My Section")             ;; => (heading . "My Section")
(org-link-parts "notes.org::*Heading")     ;; => (file . "notes.org")
(org-link-search "notes.org::*Heading")    ;; => "*Heading"
(org-image-link? "photo.jpeg?raw=1")       ;; => #t
#+end_src

Both renderers then ask the same questions and follow the same answer.

| Org                            | HTML                                          | Markdown                                      |
|--------------------------------+-----------------------------------------------+-----------------------------------------------|
| ~[[file:photo.png][a photo]]~    | ~<img src="photo.png" alt="a photo" />~       | ~![a photo](photo.png)~                       |
| ~[[images/diagram.svg]]~         | ~<img src="images/diagram.svg" alt="..." />~  | ~![images/diagram.svg](images/diagram.svg)~   |
| ~[[file:notes.org][notes]]~      | ~<a href="notes.org">notes</a>~               | ~[notes](notes.org)~                          |
| ~[[#custom-id][there]]~          | ~<a href="#custom-id">there</a>~              | ~[there](#custom-id)~                         |
| ~[[*My Section][up]]~            | ~<a href="#my-section">up</a>~                | ~[up](#my-section)~                           |
| ~[[https://gnu.org][GNU]]~       | ~<a href="https://gnu.org">GNU</a>~           | ~[GNU](https://gnu.org)~                      |

Two details in that table deserve a sentence each. The ~::search~ suffix is set aside before the path is used as a file name, so ~file:notes.org::*Heading~ does not produce a broken file name. And a target such as ~C:/tmp/x.txt~ is not mistaken for a link with a scheme named ~c~, because a real scheme is written in lower case; this is a small thing, and it is the kind of small thing that decides whether a program is pleasant to use on somebody else's computer.

** Figures

Org gives the element that follows a ~#+CAPTION:~ or a ~#+NAME:~ keyword a caption and a name. When that element is a link to an image, the three things are one object: a figure. The parser folds them together, so the renderers receive a single node instead of three neighbors that they must guess about.

#+begin_src scheme
(org->html "#+NAME: fig:arch\n#+CAPTION: The architecture\n[[file:diagram.png][a diagram]]\n")
;; => "<figure id=\"fig:arch\"><img src=\"diagram.png\" alt=\"a diagram\" /><figcaption>The architecture</figcaption></figure>"
#+end_src

The name the figure carries is the very identifier that a ~[[fig:arch]]~ link points at, so the cross-reference cannot break. Both facts come from one place, and one place cannot disagree with itself.

#+begin_src scheme
(org->html "#+NAME: fig:arch\n#+CAPTION: The arch\n[[file:a.png]]\n\nSee [[fig:arch]].\n")
;; => "<figure id=\"fig:arch\">...</figure><p>See <a href=\"#fig:arch\">fig:arch</a>.</p>"
#+end_src

Markdown has no ~figure~ element, so it receives the image, the caption as an emphasised line, and an explicit anchor for the cross-reference. What counts as a figure is deliberately narrow: the keywords must sit immediately before a paragraph that holds exactly one image link and nothing else. Everything else remains a keyword line. Inventing a caption for an element this parser does not caption is worse than saying nothing, because the reader of the output would never learn that something had been silently dropped.

** Named elements

A figure is the image case of a more general rule. A ~#+NAME:~ line names the element that follows it, and any element that renders as something a link can land on can be named: a table, a source block, a quote, a list, a separator, a paragraph.

#+begin_src scheme
(org->html "#+NAME: tbl:users\n| Users | 1024 |\n\nSee [[tbl:users]].\n")
;; => "<table id=\"tbl:users\">...</table><p>See <a href=\"#tbl:users\">tbl:users</a>.</p>"
#+end_src

HTML puts the identifier on the element itself. Markdown has no element to hang it on, so it emits an explicit anchor in front, exactly as it does for a figure. A bare target that happens to be the name of an element in the same document is resolved as a cross-reference, which is why ~[[tbl:users]]~ and ~[[notes]]~ work. A target that already says what it is, by having a scheme, a ~file:~ prefix, a leading ~#~ or ~*~, or a ~::search~ suffix, keeps the meaning it wrote.

There is one deliberate asymmetry, and it is documented rather than hidden. A ~#+CAPTION:~ in front of a named table is not folded into it, because captions on tables are not rendered yet. The parser does not pretend otherwise; the line stays an ordinary keyword line where the writer put it.

** Tables, read by their bars

Tables looked finished until I examined the edges. What should ~|~ on a line of its own be? What is ~| a ||~? What happens to a row that ends the input with no newline?

The old pattern counted separators and produced one cell for each, which meant that a row with no cells in it could raise an error, and a row that ended the input acquired a phantom empty cell from the newline it did not have. The rewrite reads a row the way Org reads it: by the bars that separate the cells, where a bar closes a row when nothing but the end of the line follows it. That single rule answers all three questions at once.

- A line that is only its closing bar (~|~ on its own) is a row of *one empty cell*, not a row with no cells.
- ~| a ||~ is a row of *two cells*, the second of them empty, rather than a paragraph.
- A row that ends the input keeps exactly the cells that were written.

An empty cell also keeps its column, because an empty value is now the empty string instead of the bare tag symbol that an empty ~(* ...)~ match leaves behind. The difference sounds academic until it is your table.

** Lists that mix and nest

Org lets a list change its bullet type part-way through, and it lets a nested list use a different kind from its parent. So the grammar stopped having three separate list productions and grew one.

#+begin_src scheme
(define-peg-pattern org-list all
                    (+ (or desc-item unordered-item ordered-item)))
#+end_src

The renderers group consecutive items of the same kind into the proper element, which is what makes ~- outer~ with ~1. nested~ inside it come out as an unordered list containing an ordered one. Checkboxes, description items and arbitrary nesting depth follow from the same rule.

** The rest of the surface

Between those features and the earlier work, the supported set is now this: headings with TODO keywords, priorities and tags; paragraphs; unordered, ordered and description lists in any mixture and at any depth; checkboxes; tables with empty cells; source, example, quote, verse, center, export and comment blocks; keywords and in-buffer settings; comments; fixed-width lines; separators; footnotes, whether references, definitions or inline; bold, italic, underline, strikethrough, code, verbatim, superscript, subscript, escaped markup and forced line breaks; links with and without descriptions, bare uniform resource locators, images, figures, named elements and heading anchors.

That is most of what people actually write. It is not all of Org, and the manual says so in a section that lists the gaps rather than hiding them, because a library that lies about its coverage wastes the time of everyone who trusts it.

* Measuring the work

Before optimizing anything I wanted a benchmark that could tell me whether a change had helped, and that could not be fooled by the change itself.

The benchmarks live in ~test/veritas/benchmark/scope.scm~. They are written with the same [[https://codeberg.org/jjba23/veritas][Veritas]] framework as the unit suite, and they are selected by test type so that they never slow down ~maak test~.

#+begin_src shell
VERITAS_TEST_TYPE=benchmark \
guix shell -m manifest.scm -- guile -L ./src -L ./test \
  -c '((@ (veritas runner) run-tests))'
#+end_src

The suite measures five workloads and prints three tables, one for wall clock, one for allocation, and one for the collapse pass, formatted as Markdown and ready to paste into the manual. That last detail matters more than it may appear. A number that must be retyped by hand is a number that quietly stops being true.

| Workload                               | What it exercises                                        |
|----------------------------------------+----------------------------------------------------------|
| Parse the feature fixture              | every construct the parser knows, in 1.8 KB              |
| Parse README.org                       | a real 58 KB document with prose, tables and code blocks |
| Render the feature fixture to HTML     | parsing plus the HTML renderer                           |
| Render the feature fixture to Markdown | parsing plus the Markdown renderer                       |
| Parse a 50-clause inline paragraph     | the inline grammar, under maximum pressure               |

** Five runs, keep the fastest

A single wall clock measurement on a laptop is not a measurement. It is a rumor. The suite runs each workload five times and reports the fastest run, on the theory that the other four were interrupted by something (a browser, a compiler, the collector's own cycle arriving at an inconvenient moment) and that this one was not.

This is not statistical purity, and I do not present it as such. It is a lower bound on the cost of the work, measured on a machine that is also doing other things. The allocation figures are the stable half of the table and stay within a few percent; the wall clock moves by ten to twenty percent between sessions. If you repeat the measurements and get a different number, you have not found an error. You have found the noise, and you should suspect anyone who reports wall clock figures without it.

** Allocation, not only time

Guile's collector is good enough that one can write a parser which allocates a megabyte for every kilobyte of input and still call it fast, right up until it is embedded in a server that must serve several documents at once. So the suite measures the heap as well. The heap is collected before each workload, and what is reported is ~heap-total-allocated~: everything the workload asked for, including the garbage it dropped immediately. That measures allocation pressure, which is what triggers collections, rather than the memory that a result keeps.

The last column of that table is Guile's own ~gc-time-taken~, which is collector *processor* time. Guile sums the time of its marker threads, so a single full collection of a large heap can be reported as several times its wall clock cost on a machine with many cores. Read it as an indication of how much collector work a workload causes, not as a share of the clock. I say the same thing in the benchmark's docstring, because a number that is easy to misread will be misread.

** Fragments and the collapse pass

The last measurement in the suite is the one that eventually explained everything: how many string *fragments* a parse hands to the pass that merges them, and how long the merging takes.

Consider a pattern written as ~(* (and (not-followed-by eol) peg-any))~, which means "consume characters until the newline". The compiled pattern produces one parse object and one string fragment for every character. A line of ~n~ characters costs ~n~ one-character substrings, ~n~ list cells, and then a merge over all of them. For a document of short lines nobody notices. For a 45 KB line it is the whole program.

The fragment table made that visible without any profiling at all.

| Document                 | Fragments handed to the collapse pass | Collapse (ms) |
|--------------------------+--------------------------------------+---------------|
| Feature fixture (1.8 KB) |                                   82 |         0.043 |
| README.org (58 KB)       |                                1,264 |         0.385 |
| Plain prose (32 KB)      |                                  400 |         0.216 |
| One 45 KB line           |                                    1 |         0.005 |

The last row is the interesting one. Forty-five kilobytes of text arrive as a single fragment, because a run scanner took them in one substring instead of forty-five thousand. The README, with 58,523 bytes of input, arrives as 1,264 fragments, roughly one per line of prose, instead of one per character.

* What the profile said

Veritas profiles every benchmark with Guile's ~statprof~, and that is what turned a vague impression that the parser was slow on large files into a definite statement about one procedure.

I fed the old parser a document consisting of one 40 KB line and looked at the profile.

#+begin_example
%     cumulative   self              procedure
 97.55      1.77      1.77  list?
  0.61    115.98      0.01  ice-9/boot-9.scm:220:5:map1
  0.61      0.03      0.01  orgwebalchemy/peg.scm:339:0
  0.61      0.01      0.01  reverse
  0.00  23786.61      0.00  ice-9/peg/simplify-tree.scm:48:0:string-group
  0.00      3.56      0.00  ice-9/peg/simplify-tree.scm:65:0:string-collapse
#+end_example

97.55 percent of the time is inside ~list?~. Not in the grammar, not in the renderers, not in any of my own code: in a single predicate, called by Guile's own tree simplifier.

This is why one profiles. My hypothesis was that the PEG engine was slow. The truth was that a helper in ~(ice-9 peg simplify-tree)~ asks ~(list? lst)~ of the rest of the list at every level of its recursion, and therefore walks the list quadratically.

Here is the relevant part of ~string-group~.

#+begin_src scheme
(define (string-group lst)
  (if (not (list? lst))       ;; <- O(length) at every level
      lst
      (if (null? lst)
          '()
          (let ((next (string-group (cdr lst))))   ;; non-tail recursion
            ...))))
#+end_src

For a run of ~n~ fragments this is about ~n²/2~ list steps. A line of 40,000 characters means 800 million of them, which is precisely the 1.77 seconds that the profile reports. Doubling the line quadruples the bill, and the measurements agree: 20 KB took 423 ms and 40 KB took 1,761 ms.

So there were two problems, and only one of them was mine. My grammar produced one fragment per character, which handed the quadratic pass an enormous run to chew on. And the collapse pass was quadratic in the length of a run, so that even a modest run cost more than it should. Repairing only the first would have left a slow path waiting for anyone who writes a long line. Repairing only the second would have left megabytes of pointless allocation. Both had to go.

* The two rounds of repair

** First round: fast paths in the grammar

The first round was micro-optimization of the grammar. It helped, though not where I expected.

The scheme alternation used to be fifteen whole-string comparisons.

#+begin_src scheme
(define-peg-pattern url-scheme all
                    (or "http://" "https://" "ftp://" "ftps://"
                        "file://" "ssh://" "sftp://" "ws://" "wss://"
                        "git://" "gopher://" "tel:" "mailto:"
                        "irc://" "ircs://"))
#+end_src

Grouping the alternatives by their first character means that a position which cannot begin a scheme fails after one comparison instead of fifteen.

#+begin_src scheme
(define-peg-pattern url-scheme all
                    (or (and "h" (or "ttps://" "ttp://"))
                        (and "f" (or "tps://" "tp://" "ile://"))
                        (and "s" (or "sh://" "ftp://"))
                        (and "w" (or "ss://" "s://"))
                        (and "g" (or "opher://" "it://"))
                        "tel:"
                        "mailto:"
                        (and "i" (or "rcs://" "rc://"))))
#+end_src

The alternation of inline constructs was also in a poor order. It tried the multi-character constructs, footnotes and links and the scheme scan, before the single-character markers, so a line full of ~*bold*~ and ~/italic/~ paid for the expensive branches first. Putting the one-character markers first and the link and uniform resource locator machinery last costs nothing.

#+begin_src scheme
(define-peg-pattern inline-special body
                    (or inline-bold inline-italic inline-code inline-verbatim
                        inline-underline inline-strike
                        inline-superscript inline-subscript
                        inline-line-break inline-escape
                        inline-footnote-inline inline-footnote-def inline-footnote-ref
                        inline-link-with-desc inline-link-no-desc
                        inline-raw-url))
#+end_src

I also added a hand-written class for plain characters, so that a run of ordinary text could be taken with a few range tests instead of a ~not-followed-by~ check against the whole inline grammar at every position.

The result of this round was that the inline benchmark doubled, the document benchmarks improved by about a third, and *the single-line case did not move at all*. That last fact was the useful part, because it told me that the remaining cost was not in the grammar.

** Second round: run scanners

A compiled PEG pattern in Guile is only a procedure of ~(string length position)~ that returns ~(end . body)~ or ~#f~. Nothing prevents you from writing that procedure by hand and naming it in the grammar like any other pattern. This is the whole idea of the run scanners: find the end of a run in a single C-level scan with ~string-index~, and return one substring.

#+begin_src scheme
(define (run-end str len pos stop-chars stop?)
  "Return the end of the run from POS that stops at the first character
of STOP-CHARS at which STOP? holds, or at LEN."
  (let loop ((i pos))
    (let ((candidate (or (string-index str stop-chars i len) len)))
      (if (or (>= candidate len) (stop? str len candidate))
          candidate
          (loop (1+ candidate))))))

(define (text-run str len pos stop-chars stop?)
  (let ((end (run-end str len pos stop-chars stop?)))
    (list end (substring str pos end))))

(define (line-text-scanner str len pos)
  "Consume the rest of the line as one string."
  (text-run str len pos nl-chars always-stop))

(define-peg-pattern line-content all line-text-scanner)
#+end_src

There are thirteen such scanners now, one for each construct whose body is "text up to a delimiter": a line, a table cell, a link target, a link description, a footnote body, a keyword value, the body of a source block, a description key, the body of a raw uniform resource locator.

The delicate part is the ~stop?~ predicate. For a line, every newline really does end the run. For inline text, an asterisk ends the run only if ~inline-special~ really matches there; otherwise it is an asterisk in the middle of a sentence. So the scanner stops at every candidate, asks the grammar whether something begins there, and if not, continues after that character. The scan is still one ~string-index~ call per candidate, and there is at most one candidate per markup character in a line.

Thirteen scanners would be a maintenance problem if each one had its own idea of where text ends, so the character sets live in one place, each with a comment that says who stops there.

#+begin_src scheme
(define nl-chars (char-set #\newline #\return))
(define table-stop-chars (char-set #\| #\newline #\return))
(define inline-stop-chars
  ;; every character that can begin an inline construct: the markup markers,
  ;; the letters a raw URL scheme can start with, and the newline
  (char-set #\* #\/ #\~ #\= #\_ #\+ #\^ #\\ #\[
            #\h #\f #\s #\w #\g #\t #\m #\i #\r
            #\newline #\return))
(define link-stop-chars (char-set #\] #\newline #\return))
#+end_src

** Second round, second part: a linear collapse pass

The other half of the repair was to stop depending on the quadratic ~string-collapse~. The library now has its own ~collapse-tree~, which keeps the exact contract of Guile's procedure. Children are collapsed before their parent, a maximal run of adjacent strings becomes their concatenation, a list of strings does not join the run around it, and a result of one element is unwrapped. The difference is that the grouping is done in one pass with one ~reverse~.

#+begin_src scheme
(define (string-group-linear lst)
  (let loop ((nodes lst) (run '()) (out '()))
    (cond
      ((null? nodes)
       (reverse (if (null? run) out (cons (reverse run) out))))
      ((string? (car nodes))
       (loop (cdr nodes) (cons (car nodes) run) out))
      (else
       (loop (cdr nodes) '()
             (if (null? run)
                 (cons (car nodes) out)
                 (cons (car nodes) (cons (reverse run) out))))))))
#+end_src

Because it is the same contract and not merely a similar one, the trees it produces are identical. That is what made it possible to prove the rewrite safe instead of hoping that it was. On its own it is a factor of 533 at 32,000 fragments.

| Parse the 50-clause inline paragraph |        5,662.44 |            2,737.86 |     1,691.05 |

Parsing the 58 KB README now allocates about 68 bytes for every input byte, where it used to allocate roughly 530. That is the difference between a parse which reliably triggers a collection of its own and one which often does not.

** One long line: from eight seconds to a third of a millisecond

The clearest way to see the quadratic is to hold everything else constant and grow a single line. Here is a document whose entire content is one line of plain prose.

| Line length | Before (ms) | Fast paths (ms) | Now (ms) |
|-------------+-------------+-----------------+----------|
| 5 KB        |       26.40 |           26.25 |     0.07 |
| 10 KB       |      108.61 |          104.98 |     0.08 |
| 20 KB       |      423.39 |          408.36 |     0.12 |
| 40 KB       |    1,760.96 |        1,634.68 |     0.22 |
| 80 KB       |    8,178.63 |        7,114.17 |     0.37 |

Read the first two columns and note that each doubling of the line multiplies the time by four. That is a quadratic curve, and the grammar fast paths barely dented it, because per-character fragments and a quadratic merge are exactly what fast paths in the grammar do not touch. Now read the third column: each doubling roughly doubles the time, because ~string-index~ runs at memory speed and there is one fragment per line instead of one per character.

At 80 KB the difference is about a factor of 22,000. That is the extreme end of the curve. The realistic headline is the factor of 6.4 on the README, where the time is spread across a whole document instead of concentrated in one pathological line.

** The collapse pass on its own

To separate the two effects I benchmarked Guile's ~string-collapse~ against the library's ~collapse-tree~ on plain lists of string fragments, with no parser and no renderers involved.

| Fragments | ~string-collapse~ (ms) | ~collapse-tree~ (ms) |
|-----------+------------------------+----------------------|
|     2,000 |                   3.77 |                0.094 |
|     4,000 |                  15.35 |                0.174 |
|     8,000 |                  58.60 |                0.371 |
|    16,000 |                 240.70 |                0.718 |
|    32,000 |               1,001.63 |                1.880 |

Four times per doubling on the left, two on the right. That is the entire story of the profile in one table, and it is the kind of experiment I would like to see more often in discussions of performance: isolate the suspected cause, remove everything else, and let the numbers speak.

** What the profile looks like now

The purpose of a rewrite is that the profile stops pointing at one thing. Parsing the README two hundred times now gives this.

#+begin_example
%     cumulative   self              procedure
 26.32      0.75      0.75  %after-gc-thunk
  8.27      0.41      0.24  string-append
  6.02      0.17      0.17  string=
  4.51      0.24      0.13  orgwebalchemy/peg.scm:99:0
  4.51      0.15      0.13  reverse
  3.76      0.15      0.11  string-group-linear
  3.01      1.43      0.09  orgwebalchemy/peg.scm:375:0
  2.26      1.86      0.06  collapse-tree

The largest single entry is now the collector itself, at about a quarter of the time. Then comes the string work that building a tree implies, then the collapse pass at a few percent, then a long tail of small pattern procedures. There is no 97 percent any more, and that is what success looks like here: further gains must now come from allocating less, not from discovering another bottleneck.

* Why you can believe the measurements

Speed is easy to claim and easy to fake, because one can make any parser faster by making it wrong. Since the work touched the scanners that decide where text ends, I needed a way to show that the language had not changed.

** Equivalence with the previous parser

The test suites cannot express "the parser still does what it did before", because they encode what it ought to do. So there is a separate check that loads the old parser and the new one into a single process, the old one under renamed modules extracted with ~git show REV:src/orgwebalchemy/peg.scm~ and its neighbours, and compares six results for every input: the document syntax tree, the inline syntax tree, and the HTML and Markdown that each renderer writes.

The scanner rewrite was checked this way on 70,858 inputs. Those included every pair of interesting characters (printable ASCII, tab, newline, carriage return, the other control characters and two multi-byte characters) as documents, as inline text, and inside a link, a footnote and a description list; the README; the test fixtures; hand-written edge cases such as markup at every position, tables with empty cells and lines without a newline; and 5,800 randomly generated documents.

The empty-value change was checked again on 38,412 of those inputs. It reported 232 differences, every one of them the change I had made on purpose. More interestingly, it found no input at all that raised an error on the new side, where the old code raised on 21 of them, each a table row with no cells in it. That is how a bug fix should appear: as a difference you can name and explain.

The table change was checked on 38,250 inputs and found 16 that parse differently. Every one of the 16 was a table line whose last bar is followed by nothing but the end of the line, which is precisely the thing that changed.

** The stop set

A run scanner may leap over a character only if it is sure that the character cannot begin a construct. If that set is wrong by one character, the scanner silently swallows the beginning of a link or a footnote, and no equivalence test against the previous parser would catch it, because the previous parser had no scanners at all.

Therefore ~inline-stop-chars~ is checked against the grammar itself: at every position where ~inline-special~ really matches, the character that begins it must be in the set. Sweeping 391,094 positions of the README, the fixtures, every pair of bytes and some random markup found 6,024 constructs and no gap.

** Three deliberate differences

Three differences came out of these runs, and all three are now pinned down by tests.

1. A run of two or more ~#+CAPTION:~ or ~#+NAME:~ lines in front of an element that is not a figure used to come out of the folding step in reverse order. It now keeps document order, which is what the documentation always claimed, and which is what a reader expects of anything called a sequence.
2. The text of something empty is now the empty string, instead of the bare tag symbol that an empty match leaves behind. This is what keeps an empty cell in its column, keeps a source block without a language rendering as a source block, and keeps an empty keyword, comment, fixed-width line, footnote or block in the document instead of making it vanish from the document altogether.
3. A table row is read by its bars, as described above.

Everything else about the parser produces identical output, and the new naming feature is an addition to the language, so it is covered by tests rather than by equivalence.

** A trap when adding tests

One trap is worth recording, because I lost an afternoon to it. Veritas collects the assertions of a test by filtering the body for procedures, so assertions wrapped in a ~let~, a ~when~ or a ~parameterize~ are silently reduced to the last one. Keep every assertion at the top level of the test body, and call a helper when you need a parameterization. The tests for the class parameters show the pattern.

* What is still expensive

Honesty is part of the design, so here is what these numbers do not say.

- *Inline parsing is the most expensive stage per byte.* A 50-clause paragraph of inline markup, 4.1 KB, takes 2.3 ms, which is about 1.8 MB per second, against 11.5 MB per second for a whole document of prose. Some of that is inherent in a grammar where every position must try the alternatives. All the same, it is the number I would attack next.
- *Allocation is still dominated by the tree.* About 68 bytes of allocation per input byte, and a quarter of the parse is the collector. A cheaper node representation, or flattening parts of the tree while parsing, would buy real time.
- *There is no incremental path.* A changed document is parsed from the beginning. For an editor or a live preview, that is the feature that would matter most, and it is the one I most want to write.
- *The benchmarks measure this implementation on its own.* They do not compare it with other Org implementations, and they do not measure the incremental case. Both would be welcome additions.

* What Org has that this library does not

The manual has a section called "Current limitations", and it exists so that this article need not pretend. The known gaps are these.

- *Captions on elements that are not figures.* A ~#+CAPTION:~ before a table, a source block or a block quote is still an ordinary keyword line, because those captions are not rendered yet. Figures are the exception, and they are done.
- *Bare superscripts and subscripts.* Only the braced forms, ~x^{2}~ and ~H_{2}O~, are recognized. The bare forms, such as ~x^2~, are not, and this is a deliberate choice rather than an oversight, since the bare form cannot always be distinguished from ordinary text.
- *Babel, the agenda, the export dispatcher.* OrgWebAlchemy is a library, not an Emacs package. It parses Org; it does not execute code blocks, and it does not integrate with Org's own export machinery.
- *The long tail.* Org contains years of conventions: ~#+ATTR_HTML~, ~#+RESULTS~, column width cookies, archived subtrees, custom TODO sequences read from the document, and more. Each one requires a decision about whether to parse it, render it or leave it as text, and this library prefers to leave it as text rather than guess.

If one of these gets in your way, that is exactly the kind of report that is worth sending, ideally with the smallest Org snippet that shows the problem.

* Distribution

A library that nobody can install is a library that nobody uses, so the packaging has caught up as well.

- *Guix.* A self-contained package recipe is in the manual, pinned at version 1.2.1 with its hash, and the project is on its way into Guix itself as ~guile-orgwebalchemy~.
- *Nix.* A ~flake.nix~ and a ~default.nix~ build the working tree with the same derivation as the nixpkgs package, so that a change which breaks one breaks the other for the same reason. They cover x86_64 and aarch64, on GNU/Linux and on Darwin.
- *Continuous integration.* Pushes to ~trunk~ trigger a Woodpecker pipeline that submits the ~maak-test~ and ~maak-deploy~ tasks to [[https://byggsteg.jointhefreeworld.org][Byggsteg]], my own continuous integration system, which is itself written in Scheme.
- *Documentation.* The manual is the library's README, and the application programming interface reference is generated from the docstrings in the source with ~guile-documenta~: [[https://jointhefreeworld.org/api-docs/orgwebalchemy/API.html][the OrgWebAlchemy API documentation]].

* Reproduce the measurements

Every number in this article comes from the repository and from commands that the manual documents. If you want to check my work, here is how.

#+begin_src shell
git clone https://codeberg.org/jjba23/orgwebalchemy.git
cd orgwebalchemy

# the unit suite
guix shell -m manifest.scm -- guile -L ./src -L ./test \
  -c '((@ (veritas runner) run-tests))'

# the benchmarks (they print the tables above)
VERITAS_TEST_TYPE=benchmark \
guix shell -m manifest.scm -- guile -L ./src -L ./test \
  -c '((@ (veritas runner) run-tests))'
#+end_src

Run them on your own machine. If your numbers are very different from mine, I would like to know, because a parser that is fast on one laptop and slow on another is a parser with a mistaken assumption hidden inside it.

* What I take from this

The lesson I keep relearning with this project is that correctness and speed are not two phases of the work. Writing the scanners forced me to state, precisely, which characters can begin a construct, and that list is now a specification which a test sweeps across 391,094 positions. The equivalence harness that showed the rewrite to be safe is also the reason I dared attempt the rewrite at all.

And there is a larger point, which is the reason I care about a parser for Org in the first place. Org mode is one of the good ideas of our time: a plain text format that people can read and write without special software, that keeps its meaning when the programs change, and that grew inside a free editor where its users could extend it. Every program that can read Org mode makes that format a little more useful, and every format that more programs can read is a format that people can trust with years of their writing.

A library such as this one is a small contribution to that. It lets a program written in Scheme read what you wrote in Org, render it as HTML that a browser can display without running anyone else's code, or as Markdown that other tools understand, and it does so under a free license, on your machine, with source you can read. The web has no shortage of ways to take a document away from its author. I would like to add one more way to give it back.
